# 캐시와 재현 가능한 빌드

빠른 빌드는 필요한 작업만 수행하고 이전 결과를 재사용합니다. 정확한 재사용을 위해서는 결과에 영향을 주는 입력을 알아야 합니다.

## 캐시 종류 구분

| 종류 | 저장하는 것 | 예시 |
| --- | --- | --- |
| 다운로드 캐시 | 받은 패키지·소스·메타데이터 | 패키지 관리자 저장소 |
| 빌드 캐시 | 입력에 대응하는 작업 결과 | 컴파일된 오브젝트, 생성 자산 |
| CI 아티팩트 | 후속 작업·배포·분석에 전달할 결과 | 실행 파일, 테스트 보고서 |

의존성 다운로드 캐시가 있어도 소스 컴파일은 필요할 수 있습니다. 배포할 파일은 캐시의 우연한 적중에 의존하지 않고 명시적인 아티팩트로 전달합니다.

## 캐시 키에 포함할 입력

개념적으로 작업 캐시 키는 다음 정보로 결정됩니다. 실제 키의 구성과 검증 방법은 도구마다 다릅니다.

```text
작업 키 = hash(
  소스·헤더·생성 입력,
  의존성,
  실행 명령과 옵션,
  툴체인·SDK,
  대상 플랫폼,
  결과에 영향을 주는 환경 설정
)
```

lockfile만 같아도 소스나 컴파일 옵션은 다를 수 있습니다. 다운로드 캐시에 적절한 키가 빌드 결과 캐시에도 충분한 것은 아닙니다. 큰 디렉터리를 CI에서 복원하는 것만으로 정확한 작업 캐시가 되는 것도 아닙니다.

입력 선언이 빠지면 바뀐 결과 대신 오래된 출력을 재사용할 수 있습니다. 캐시를 끄면 문제가 사라질 때는 입력·출력 선언과 캐시 키를 먼저 점검합니다.

## 재현성, 결정성, 격리

| 개념 | 핵심 질문 |
| --- | --- |
| 결정적 빌드(Deterministic build) | 같은 입력과 조건으로 반복 실행하면 같은 결과가 나오는가? |
| 재현 가능한 빌드(Reproducible build) | 명시한 소스·환경·절차로 다른 곳에서도 같은 바이트의 결과물을 만들 수 있는가? |
| 격리된 빌드(Hermetic build) | 선언한 입력과 도구 외에 호스트 상태나 외부 서비스에 의존하지 않는가? |

컨테이너는 환경을 맞추는 데 도움이 되지만, 변경 가능한 이미지 태그·외부 다운로드·시각 정보까지 자동으로 고정하지는 않습니다. 격리된 환경에서도 난수나 현재 시간을 결과물에 넣으면 바이트 단위 재현성이 깨질 수 있습니다.

### 결과가 달라지는 흔한 원인

- 컴파일러·링커·SDK 버전과 대상 CPU 옵션
- 고정하지 않은 전이 의존성, 시스템 라이브러리
- 빌드 시각, 난수, 파일 순회 순서
- 절대 경로, 로케일, 시간대
- 네트워크에서 빌드 중 가져오는 변경 가능한 데이터

lockfile과 도구 버전을 기록하고, 도구가 지원하면 고정된 의존성으로 설치하는 모드를 사용합니다. 지원 도구에서는 `SOURCE_DATE_EPOCH`로 타임스탬프 기준을 통일하거나 경로 매핑 옵션으로 로컬 경로 차이를 줄일 수 있습니다. 환경변수를 설정하는 것만으로 모든 도구가 이를 따르지는 않습니다.

## Debug, Release, 크로스 컴파일

Debug와 Release는 관례적인 설정 이름입니다. 디버그 정보·최적화·검사 매크로의 실제 값은 프로젝트와 툴체인 설정으로 확인합니다. 최적화된 코드에도 디버그 정보를 넣을 수 있습니다.

크로스 컴파일은 **빌드를 실행하는 플랫폼과 결과물이 실행될 플랫폼이 다른 빌드**입니다. 예를 들어 x86-64 Linux에서 ARM 보드용 실행 파일을 만듭니다.

- 대상 아키텍처용 컴파일러, 링커, 헤더, 라이브러리와 sysroot를 맞춥니다. sysroot는 대상 시스템의 헤더·라이브러리 등을 찾는 기준 디렉터리입니다.
- 빌드 중 실행하는 코드 생성 도구는 빌드 머신에서 실행 가능해야 합니다.
- 대상 바이너리는 빌드 머신에서 바로 실행되지 않을 수 있으므로 실제 장치나 에뮬레이터에서 검증합니다.
- 아키텍처·툴체인·설정별 출력과 캐시를 구분합니다. `host`·`target` 용어의 정확한 의미는 사용하는 도구 문서에서 확인합니다.

## CI 적용 순서

1. 소스 버전, lockfile, 툴체인·SDK, 빌드 옵션을 기록합니다.
2. 고정된 의존성을 준비하고 로컬과 같은 빌드 명령을 실행합니다.
3. 필요한 테스트를 실행하고 결과물을 명시적으로 수집합니다.
4. 캐시 없이 빈 출력 디렉터리에서도 성공하는지 확인합니다.
5. 바이트 단위 재현성이 필요하면 독립된 빌드끼리 해시를 비교하고 차이를 분석합니다.

서명·공증처럼 시각이나 외부 서비스를 사용하는 후처리는 별도 단계로 구분하고, 어느 단계의 결과물까지 비교할지 정합니다.

참고: [Reproducible Builds](https://reproducible-builds.org/docs/), [Bazel Hermeticity](https://bazel.build/basics/hermeticity), [CMake 툴체인](https://cmake.org/cmake/help/latest/manual/cmake-toolchains.7.html)
