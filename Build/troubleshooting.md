# 빌드 오류 진단

최종 요약인 `build failed`보다 **실패한 명령과 그 명령에서 처음 발생한 원인 오류**를 찾습니다. 병렬 로그에서는 여러 작업의 출력이 섞일 수 있습니다.

## 단계별 점검

| 증상 | 의심할 단계·원인 | 먼저 확인할 것 |
| --- | --- | --- |
| 패키지 다운로드·버전 해석 실패 | 의존성 준비 | 저장소 접근, 인증, lockfile, 도구 버전 |
| 컴파일러·생성기를 못 찾음 | 구성·생성 | 설치 여부, PATH, CMake 생성기와 툴체인 설정 |
| `header: No such file or directory` | 전처리 | include 경로, 대소문자, 생성 헤더의 선행 작업 |
| 문법·타입 오류 | 컴파일 | 해당 소스, 언어 표준, 컴파일러 버전, 조건부 매크로 |
| `undefined reference` / `unresolved external symbol` | 링크 | 정의를 포함한 오브젝트·라이브러리, C/C++ 이름 규칙, 링크 순서 |
| `multiple definition` / 중복 심볼 | 링크 | 같은 구현의 중복 포함, 헤더에 넣은 외부 정의 |
| `cannot find -l...` | 링크 | 라이브러리 검색 경로, 파일명, 설치한 개발 패키지 |
| 실행 시 공유 라이브러리 누락 | 로딩 | 런타임 라이브러리 배포, 로더 검색 경로, ABI |
| `Exec format error` | 실행 대상 불일치 등 | CPU·OS·파일 형식, 스크립트 인터프리터 |
| 병렬 빌드에서만 실패 | 의존성 누락·경합 | 생성 파일 순서, 여러 작업이 같은 파일에 쓰는지 |
| 정리 후에만 성공 | 오래된 출력·입력 추적 누락 | 헤더·옵션 의존성, 출력 경로, 캐시 키 |

일부 정적 링커에서는 라이브러리 순서가 중요합니다. GNU 계열의 일반적인 경우에는 참조하는 오브젝트 뒤에 라이브러리를 둡니다. CMake에서는 가능하면 파일 목록을 직접 조립하기보다 타깃 간 링크 관계를 선언합니다.

## 실제 실행 명령 확인

```sh
# CMake가 호출하는 빌드 명령을 자세히 출력
cmake --build build-cmake --verbose

# Ninja를 직접 사용하는 경우
ninja -C build-cmake -v

# Make가 실행할 레시피 확인
make -n
```

`make -n`은 일반 레시피를 실행하지 않고 출력하지만, 재귀 Make나 Makefile 평가 중 실행되는 명령 등 예외가 있습니다. 신뢰하지 않는 Makefile을 안전하게 분석하는 격리 수단은 아닙니다.

## 원인을 좁히는 순서

1. 실패한 명령, 작업 디렉터리, 도구 버전, 설정을 기록합니다.
2. 병렬 출력을 읽기 어렵다면 병렬 수를 1로 낮춰 오류를 확인합니다. 성공하더라도 의존성 문제가 해결됐다고 판단하지 않습니다.
3. 실패한 입력·경로·옵션을 정상 환경과 비교합니다.
4. 기존 로그와 출력을 보존한 채 새 출력 디렉터리에서 빌드해 비교합니다.
5. 캐시를 제외했을 때의 차이를 확인하고 누락된 입력이나 잘못된 설정을 수정합니다.

매번 전체 정리를 하면 증상이 숨겨질 수 있습니다. 원인을 수정한 뒤 최초 빌드, 변경 없는 재빌드, 소스·헤더 변경 후 빌드, 병렬 빌드를 확인합니다.

## 로컬에서는 되는데 CI에서 실패할 때

- 커밋하지 않은 파일이나 로컬에서만 생성된 파일을 참조하는지 확인합니다.
- 파일명 대소문자, 경로 구분, 실행 권한, 셸 차이를 확인합니다.
- 의존성·툴체인·환경 설정과 실제 실행 명령을 비교합니다.
- 종료 코드와 CI 로그로 메모리·디스크 부족 여부를 확인합니다. 병렬 작업 수가 많으면 메모리 사용량도 커질 수 있습니다.
