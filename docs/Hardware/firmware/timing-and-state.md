# 시간과 상태 관리

여러 장치를 제어하려면 “무엇을 할지”뿐 아니라 “언제 시작하고 언제 포기할지”를 정해야 합니다.

먼저 알면 좋은 개념: [ISR·원자성·임계 구역·단조 시간](../glossary/firmware.md#시간과-동시성), [레지스터 접근과 경쟁 문제](../background/register-side-effects.md)

## 폴링과 인터럽트

| 방식 | 동작 | 적합한 상황 | 주의점 |
| --- | --- | --- | --- |
| 폴링 | 반복해서 상태 확인 | 느린 센서, 단순한 입력 | 확인 간격 사이의 짧은 이벤트를 놓칠 수 있음 |
| 인터럽트 | 이벤트 발생 시 처리 루틴 실행 | 펄스, 데이터 준비, 빠른 반응 | 공유 상태, 우선순위, 실행 시간 관리 필요 |

인터럽트 서비스 루틴(ISR)은 짧게 유지합니다. 플래그·카운터·큐로 이벤트를 전달하고 긴 계산이나 통신은 일반 실행 흐름에서 처리합니다. ISR 안에서 블로킹 대기나 해당 환경에서 허용되지 않는 API를 호출하지 않습니다.

플래그 하나는 여러 이벤트를 하나로 합칠 수 있습니다. 모든 펄스를 세어야 한다면 카운터·큐·하드웨어 캡처를 고려합니다. ISR과 일반 코드 사이의 데이터 공유에는 원자성이나 임계 구역이 필요할 수 있습니다. **원자성**은 다른 실행 흐름이 중간 상태에 끼어들어 깨뜨릴 수 없는 하나의 동작처럼 수행되는 성질이고, **임계 구역**은 공유 자원 접근을 보호해야 하는 코드 구간입니다.

## 블로킹 지연과 주기 실행

`1초 대기 → 센서 읽기` 방식은 단순하지만, 기다리는 동안 같은 실행 흐름에서 버튼·통신을 처리하지 못합니다.

```text
마지막_측정 = 현재 시각

반복:
    now = 현재 시각
    버튼 처리
    수신 데이터 처리

    경과시간(now, 마지막_측정) >= 측정_주기 이면:
        마지막_측정 = now
        센서 측정 작업 시작
```

이 방식도 작업 자체가 오래 걸리면 지연됩니다. 정밀한 PWM·펄스 간격은 일반 반복문 대신 하드웨어 타이머를 사용합니다. OS 사용자 공간에서는 스케줄링 지연도 고려합니다.

`마지막_측정 = now`는 늦어진 주기를 건너뜁니다. `마지막_측정 += 주기`는 기준 주기를 유지하지만 밀린 작업을 연속 실행할 수 있으므로, 누락·추격 정책을 정해야 합니다.

## 시간 카운터의 래핑

고정 폭 카운터는 최댓값을 넘으면 0으로 돌아갈 수 있습니다. 경과 시간 계산에는 보통 같은 폭의 부호 없는 뺄셈을 사용합니다.

```text
N비트 카운터에서:
elapsed = (now - start) mod 2^N
```

시작부터 관찰 시점까지 실제 경과가 카운터 한 바퀴보다 짧다는 조건이 필요합니다. 충분히 자주 확인하고, 모호성을 피하도록 대기 구간을 보수적으로 반 주기보다 작게 제한하는 설계가 흔합니다. 달력 시각 대신 단조 증가하는 시간원을 사용합니다.

## 센서 상태 머신 예시

```text
IDLE → 측정 명령 전송 성공 → WAITING
WAITING → 데이터 준비 확인 → READING
READING → 수신·검증 성공 → IDLE

명령 실패 / 준비 시간 초과 / 수신 오류 → ERROR
ERROR → 재시도 횟수 이내이고 대기 시간 경과 → 재초기화 후 IDLE
ERROR → 재시도 한도 초과 → FAULT
FAULT → 오류 표시와 안전 상태 유지, 명시적 복구를 기다림
```

- 각 통신 호출 자체에도 타임아웃이 있어야 합니다.
- 재시도 횟수와 간격을 제한합니다.
- 오래된 값은 최신 값과 구별하고, 실패를 정상 측정값 `0`으로 바꾸지 않습니다.
- 모터 등 출력 장치는 통신·센서 오류 시 어떤 상태로 이동할지 정합니다.
- watchdog은 정지한 펌웨어를 재시작하는 보조 수단입니다. 재시작 전후의 출력 상태도 설계해야 합니다.
