# 웹훅(Webhook) 설계와 수신

> 서버가 **먼저** 알려 주는 API. 보내는 쪽은 재시도·서명을, 받는 쪽은 검증·중복 처리를 책임진다

웹훅은 이벤트가 생기면 서비스가 상대 서버의 URL로 HTTP 요청을 보내는 방식입니다. "역방향 API"라고 부르기도 합니다. 폴링보다 지연이 짧고 요청이 적지만, **받는 쪽이 공개 URL을 열어 두어야** 하므로 보안과 신뢰성 문제가 따라옵니다.

이 문서는 오픈 명세 **Standard Webhooks 1.0.0**의 권고를 기준으로 합니다. IETF 표준이 아니라 **업계 합의를 모은 명세**이며, 개별 서비스(Stripe, GitHub 등)는 헤더 이름과 서명 방식이 다릅니다.

> **서명·검증 코드는 직접 실행해서 확인했습니다**(Node 24.13, `node:crypto`). 실제 네트워크 전송, 재시도 스케줄러, 개별 서비스의 웹훅은 실행하지 않았습니다.

---

## 개념: 웹훅이 신뢰성 문제인 이유

| 문제 | 왜 생기나 | 해법 |
| --- | --- | --- |
| **위조** | 공개 URL이라 누구나 POST할 수 있음 | 서명 검증 |
| **재생(replay)** | 유효한 요청을 가로채 다시 보낼 수 있음 | 타임스탬프 허용 오차 |
| **중복 전달** | 수신 측이 응답을 늦게 주면 발신 측이 재시도함 | 이벤트 ID로 멱등 처리 |
| **유실** | 수신 서버가 내려가 있음 | 발신 측 재시도(지수 백오프) |
| **순서 뒤바뀜** | 재시도 때문에 나중 이벤트가 먼저 도착함 | 타임스탬프/상태 재조회 |

웹훅은 기본적으로 **"최소 한 번(at-least-once)" 전달**로 설계합니다. 정확히 한 번 보장은 어렵기 때문에, 받는 쪽이 **중복을 견디게** 만드는 것이 핵심입니다([멱등성](./idempotency.md)과 같은 발상).

## 페이로드 구조

명세의 권고입니다.

```json
{
  "type": "contact.created",
  "timestamp": "2022-11-03T20:26:10.344522Z",
  "data": { "id": "1f81eb52-5198-4599-803e-771906343485" }
}
```

- `type`: 마침표로 구분한 **계층형 이벤트 이름**(`invoice.paid`). 같은 타입은 항상 같은 스키마여야 함
- `timestamp`: 이벤트가 **발생한** 시각(ISO 8601). 전송 시도 시각과 다를 수 있음
- `data`: 이벤트 데이터

### 얇은(thin) 페이로드 vs 가득 찬(full) 페이로드

| | thin (ID만) | full (전체 상태) |
| --- | --- | --- |
| 장점 | 작고, 민감 데이터가 덜 나감, 항상 **최신 상태**를 API로 조회 | 수신 측이 추가 API 호출 없이 처리 |
| 단점 | 수신 측이 매번 API를 호출해야 함 | 순서가 뒤바뀌면 **낡은 데이터**를 쓸 수 있음 |

명세는 페이로드를 **작게(보통 20KB 미만)** 유지하라고 권고합니다. 큰 데이터는 링크로 전달합니다.

## 서명 검증

명세의 스킴: **메시지 ID, 타임스탬프, 본문을 `.`로 이어서** 서명합니다.

```
signed_content = webhook-id + "." + webhook-timestamp + "." + 본문(raw)
```

| 헤더 | 의미 |
| --- | --- |
| `webhook-id` | 이벤트 고유 ID. **재시도해도 같은 값** |
| `webhook-timestamp` | 전송 시도 시각(초 단위 유닉스 시간) |
| `webhook-signature` | **공백으로 구분한 서명 목록** (`v1,<base64> v1a,<base64>`) |

| | 대칭 | 비대칭 |
| --- | --- | --- |
| 알고리즘 | HMAC-SHA256 (`v1`) | ed25519 (`v1a`) |
| 비밀 형식 | `whsec_` + base64 | `whsk_`(비밀), `whpk_`(공개) |
| 특징 | 빠르고 단순. 양쪽이 비밀을 가짐 | 수신 측은 공개키만 가지므로 **더 안전** |

서명 목록이 여러 개인 이유는 **키 교체 시 무중단**을 위해 옛 키와 새 키로 모두 서명해 보내기 때문입니다.

### 직접 돌려 본 검증 결과

```js
const sign = (id, ts, raw) =>
  'v1,' + createHmac('sha256', secret).update(`${id}.${ts}.${raw}`).digest('base64');

function verify(h, raw, now = Math.floor(Date.now()/1000), tol = 300) {
  const ts = Number(h['webhook-timestamp']);
  if (!Number.isInteger(ts) || Math.abs(now - ts) > tol) return 'rejected: timestamp';
  const exp = Buffer.from(sign(h['webhook-id'], ts, raw));
  for (const s of h['webhook-signature'].split(' ')) {
    const got = Buffer.from(s);
    if (got.length === exp.length && timingSafeEqual(got, exp)) return 'ok';
  }
  return 'rejected: signature';
}
```

| 시도 | 결과 |
| --- | --- |
| 원본 본문 그대로 | `ok` |
| **JSON을 파싱했다가 다시 직렬화**(들여쓰기 추가) | **`rejected`** |
| 본문 한 글자 변경 | `rejected` |
| `webhook-id`만 변경 | `rejected` |
| 10분 뒤 재전송(허용 오차 5분) | `rejected: timestamp` |
| 옛 서명 + 현재 서명이 함께 있음 | `ok` |
| 길이가 다른 서명 | `rejected` |

### 검증에서 자주 틀리는 것

- **원본 바이트(raw body)로 검증해야 합니다.** 프레임워크가 JSON을 파싱한 객체를 다시 `JSON.stringify`하면 공백·키 순서가 달라져 위 표의 둘째 줄처럼 **정상 요청도 거부**됩니다. Express라면 `express.json()` 앞에서 raw body를 따로 보관합니다.
- **상수 시간 비교**(`timingSafeEqual`)를 씁니다. 일반 `===`는 일치하는 앞부분 길이에 따라 시간이 달라져 서명을 추측당할 수 있습니다(명세의 권고). `timingSafeEqual`은 **길이가 다르면 예외**를 던지므로 위 코드처럼 길이를 먼저 비교합니다.
- **타임스탬프 허용 오차**로 재생을 막습니다. 위 실험은 5분을 썼는데, 적정값은 서비스 정책에 따릅니다.
- 서명 대상에 ID와 타임스탬프를 넣는 이유는, 본문만 서명하면 **헤더를 바꿔 재생**할 수 있기 때문입니다. ID·타임스탬프에 `.`이 들어가지 않게 해야 합니다.
- 검증 키는 **엔드포인트별로 고유**하게 둡니다. 고객 간에 재사용하면 한 고객이 다른 고객 이름으로 서명을 만들 수 있습니다.

## 받는 쪽: 빨리 응답하고, 중복을 견딘다

```
1. 서명·타임스탬프 검증 (실패 → 4xx)
2. webhook-id를 이미 처리했는가? (예 → 2xx로 무시)
3. 이벤트를 큐/DB에 저장
4. 즉시 2xx 응답   ← 무거운 처리는 이 뒤에 비동기로
```

- 발신 측은 **15~30초 안에 2xx**를 받지 못하면 실패로 보고 재시도합니다(명세 권고). 응답 전에 무거운 작업을 하면 타임아웃 → 재시도 → **중복**이 됩니다.
- `webhook-id`를 멱등 키로 씁니다. 명세의 예시는 Redis에 5분간 저장하는 것인데, **재시도 기간(며칠)이 더 길면 저장 기간도 그에 맞춰야** 합니다.
- **순서를 가정하지 않습니다.** `updated` 다음에 `created`가 올 수 있으므로, 이벤트의 타임스탬프를 비교하거나 상태를 API로 다시 조회합니다.
- 이벤트 처리 로직은 **같은 이벤트를 두 번 받아도 결과가 같게** 작성합니다(예: "잔액 += 10"이 아니라 "결제 ID 123을 완료 처리").

## 보내는 쪽: 재시도와 실패 처리

### 성공·실패 판정과 상태 코드 처리

| 응답 | 발신 측 동작 (명세 권고) |
| --- | --- |
| `2xx` | 성공 |
| `3xx` | **실패.** 리다이렉트를 따라가지 않고 URL을 갱신하게 함 |
| `410 Gone` | 수신자가 더 안 받겠다는 뜻 → **엔드포인트를 비활성화** |
| `429`, `502`, `504` | 과부하 신호 → **전송 속도를 늦춤** |
| 그 외 | 실패 |
| `Retry-After` 헤더 | 다음 시도 시각 결정에 반영 |

### 재시도 스케줄

명세는 **며칠에 걸친 지수 백오프 + 무작위 지터**를 권하고, 예시로 즉시 → 5초 → 5분 → 30분 → 2시간 → 5시간 → 10시간 → 14시간 → 20시간 → 24시간(첫 시도 후 약 75시간)을 듭니다. 장시간 계속 실패하면 **다른 채널(이메일 등)로 알리고 엔드포인트를 비활성화**하는 것도 권장합니다. 지터는 수신 서버가 복구되는 순간 재시도가 한꺼번에 몰리는 것을 막습니다.

### SSRF 방어 (보내는 쪽)

고객이 웹훅 URL을 등록할 수 있으면 **내부 주소**(`http://169.254.169.254/`, `http://localhost:…`, 사설 IP)를 등록해 서버가 내부 서비스를 호출하게 만들 수 있습니다. 명세의 방어책은 웹훅 요청을 **내부망에 접근할 수 없는 전용 프록시/네트워크**에서 보내는 것입니다. 추가로 HTTPS를 강제하고, 도메인을 IP로 풀어 본 뒤 내부 대역이면 거부합니다(DNS를 나중에 바꾸는 우회까지 고려해 **연결 시점의 IP를 검사**). 이 부분은 코드로 실행하지 않았습니다.

### 있으면 좋은 것

- 수신자가 **이벤트 타입을 골라서** 구독(발신 측에서 필터링 → 불필요한 요청 감소)
- 전달 이력·실패 사유 조회, **수동 재전송** 기능
- 엔드포인트 등록·조회 API와 서명 키 교체 절차

## 🎯 체크리스트

### 받는 쪽
- [ ] **원본 본문**으로 서명 검증 (파싱 후 재직렬화 금지)
- [ ] 상수 시간 비교 사용 (`timingSafeEqual`, 길이 먼저 확인)
- [ ] `webhook-timestamp` 허용 오차로 재생 방지
- [ ] `webhook-id`로 중복 제거, 보관 기간이 재시도 기간 이상
- [ ] 저장하고 즉시 2xx, 무거운 처리는 비동기
- [ ] 이벤트 순서를 가정하지 않음

### 보내는 쪽
- [ ] ID·타임스탬프·본문을 함께 서명, 엔드포인트별 고유 키
- [ ] 키 교체용 다중 서명 지원
- [ ] 지수 백오프 + 지터, 재시도 기간 공개
- [ ] 3xx는 실패로 처리, 410이면 비활성화, 429/502/504에서 속도 조절
- [ ] 요청 타임아웃(15~30초), HTTPS 강제, SSRF 방어
- [ ] 이벤트 스키마를 문서화([OpenAPI](./openapi.md)의 `webhooks`)
