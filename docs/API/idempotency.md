# 멱등성과 안전한 재시도

> 네트워크는 실패하고 클라이언트는 다시 보낸다. **같은 요청이 두 번 와도 결과가 한 번과 같게** 만드는 방법

HTTP 메서드의 안전·멱등 정의는 [API Design](./api-design.md#http-메서드의-의미-안전safe과-멱등idempotent)에 있습니다. 이 문서는 그 뒤 단계, 즉 **`POST`처럼 멱등하지 않은 요청을 안전하게 재시도하게 만드는 서버·클라이언트 설계**를 다룹니다.

> **서버 흐름은 직접 실행해서 확인했습니다.** Node 24.13의 내장 SQLite(`node:sqlite`)로 아래 4가지 경우를 돌려 결과를 얻었습니다. 단일 프로세스·메모리 DB라서 **동시에 들어오는 진짜 병렬 요청과 서버 크래시는 재현하지 못했습니다.**

---

## 개념: 왜 재시도가 위험한가

클라이언트가 `POST /orders`를 보냈는데 **응답이 오지 않았다면**, 가능한 상황은 셋입니다.

| 상황 | 서버의 실제 상태 | 클라이언트가 아는 것 |
| --- | --- | --- |
| 요청이 서버에 도달하지 못함 | 주문 없음 | 응답 없음 |
| 처리했지만 응답이 유실됨 | **주문 있음** | 응답 없음 |
| 아직 처리 중 | 곧 주문 생김 | 응답 없음 |

클라이언트는 셋을 **구분할 수 없습니다.** 다시 보내면 첫째는 정상이지만 둘째는 **주문이 두 번** 생깁니다. 안 보내면 첫째에서 주문이 사라집니다. 결제·주문·메시지 발송처럼 되돌리기 어려운 작업에서 이 문제가 실제 사고가 됩니다.

해결은 "재시도하지 말자"가 아니라 **서버가 재시도를 알아보게 만드는 것**입니다.

---

## 멱등 키(Idempotency-Key)

클라이언트가 **사용자의 의도 하나당 고유한 키 하나**를 만들어 모든 재시도에 같은 값으로 보냅니다. 서버는 키를 기억해 두었다가 같은 키가 오면 **다시 처리하지 않고** 처음 결과를 돌려줍니다.

```http
POST /orders
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"
Content-Type: application/json

{"item": "book"}
```

IETF 드래프트(draft-ietf-httpapi-idempotency-key-header-08, 2026-10-22)에서 확인한 규칙입니다. **아직 RFC가 아닌 인터넷 드래프트**라서 내용이 바뀔 수 있습니다.

| 항목 | 내용 |
| --- | --- |
| 값 형식 | Structured Field의 **String**이라 **큰따옴표로 감쌈** (`"8e03…"`) |
| 고유성 | 키는 유일해야 하고, **다른 요청 본문에 재사용하면 안 됨** (MUST NOT). UUID 같은 무작위 값 권장 |
| 만료 | 서버가 만료 정책을 정하고 **문서에 공개**해야 함 (SHOULD) |
| 지문(fingerprint) | 본문 체크섬 등으로 만들어 키와 함께 비교할 수 있음 (MAY) |
| 서버 문서 | 멱등 관련 명세(만료 정책 포함)를 **공개해야 함** (MUST) |

### 서버의 판단 흐름

```
키 + 지문을 처음 봄        → 정상 처리하고 응답 저장
같은 키 + 같은 지문, 이미 완료 → 저장된 응답을 그대로 반환 (재처리 X)
같은 키 + 같은 지문, 처리 중   → 409 Conflict
같은 키 + 다른 지문          → 422 Unprocessable Content
키가 필요한 작업인데 헤더 없음  → 400 Bad Request
```

드래프트는 위 세 오류 모두 **`application/problem+json`([RFC 9457](./api-design.md#표준-형식-rfc-9457-problem-details))으로, 문서 링크와 함께** 응답하도록 예시를 듭니다. 그 밖의 4xx/5xx는 각 서버의 문서를 따릅니다.

> 드래프트는 오류 후 재시도에 대해 "**409를 제외하면 클라이언트가 요청을 고친 뒤에 재시도해야 한다**"고 적습니다. 409는 기다렸다가 같은 요청을 다시 보내면 됩니다.

### 직접 돌려 본 결과

키를 `PRIMARY KEY`로 두고 `INSERT OR IGNORE`로 **먼저 선점**하는 방식입니다. 선점에 실패하면(`changes === 0`) 이미 본 키입니다.

```js
const ins = db.prepare('INSERT OR IGNORE INTO idem(key,fp) VALUES(?,?)').run(key, fp);
if (ins.changes === 0) {
  const row = db.prepare('SELECT * FROM idem WHERE key=?').get(key);
  if (row.fp !== fp)      return [422, 'key reused with different payload'];
  if (row.status === null) return [409, 'original request still in progress'];
  return [row.status, row.body];                 // 저장된 응답 재생
}
// ... 실제 처리 후 status/body 저장
```

| 호출 | 결과 |
| --- | --- |
| `k1` + `{item:'a'}` 첫 요청 | `201 {"id":1}` |
| `k1` + `{item:'a'}` 재시도 | `201 {"id":1}` (재생, **주문은 새로 생기지 않음**) |
| `k1` + `{item:'b'}` 다른 본문 | `422` |
| `k2` 선점만 하고 응답 저장 전 재시도 | `409` |
| 마지막에 `orders` 행 수 | **1** |

## 설계할 때 놓치기 쉬운 것

- **선점은 반드시 원자적이어야 합니다.** "조회 후 없으면 삽입"은 두 요청이 동시에 오면 둘 다 "없음"을 봅니다. 위 코드처럼 **유일 제약(PK/UNIQUE)** 이나 Redis의 `SET key value NX` 같은 원자 연산으로 선점합니다.
- **키만 선점하고 서버가 죽으면** `status`가 `NULL`인 행이 남아 같은 키가 계속 409를 받을 수 있습니다. 대책은 설계 사항입니다(선점과 비즈니스 처리를 **같은 트랜잭션**에 넣거나, 처리 중 표시에 **만료 시각**을 둠). 이 문서의 실험에서는 크래시를 재현하지 않았고 위 대책도 실행하지 않았습니다.
- **외부 부작용은 DB 트랜잭션 밖에 있습니다.** 결제 승인이나 이메일 발송은 롤백되지 않으므로, 외부 호출에도 **그쪽 API의 멱등 키를 전달**해야 합니다.
- **저장한 응답은 "그때의" 응답입니다.** 재생할 때 최신 상태를 다시 계산하지 않고 처음 응답을 돌려주는 것이 일관됩니다.
- **키는 사용자 범위로 구분**합니다. 서로 다른 사용자가 같은 키를 쓰는 경우를 막으려면 저장 키를 `(사용자, 키)`로 잡습니다(관례, 드래프트는 규정하지 않음).
- **만료를 둡니다.** 영원히 보관하면 저장소가 커집니다. 재시도가 의미 있는 기간(예: 24시간)을 정해 공개합니다.

## 클라이언트가 지킬 규칙

- 키는 **요청마다가 아니라 사용자 의도마다** 만듭니다. "주문 버튼 클릭" 1회 = 키 1개이고, 그 클릭의 모든 재시도는 **같은 키**를 씁니다.
- 새 주문을 만들 때는 새 키를 씁니다. 같은 키로 다른 본문을 보내면 422입니다.
- 재시도 대상은 **연결 실패·타임아웃·5xx·429**입니다. 429는 `Retry-After`를 따릅니다([429 처리](./rate-limiting.md#429-응답-처리-클라이언트)).
- 재시도에는 **지수 백오프 + 지터**를 적용해 서버가 회복 중일 때 요청이 몰리지 않게 합니다.
- 4xx(400·422 등)는 **요청을 고치지 않는 한 재시도해도 같은 결과**입니다.

> 멱등 키 헤더는 표준이 아니라 **관례**로 먼저 퍼졌습니다. 결제 업체 등이 같은 이름을 쓰지만 만료 기간·오류 코드가 업체마다 다르므로, 연동할 때는 **그 API의 문서**를 확인합니다(이 문서에서 개별 업체 문서는 확인하지 않음).

## 🎯 체크리스트

- [ ] 생성·결제처럼 되돌리기 어려운 `POST`에 멱등 키를 받는다
- [ ] 키 선점은 유일 제약이나 원자 연산으로 한다
- [ ] 같은 키 + 같은 본문 → 저장된 응답, 다른 본문 → 422, 처리 중 → 409
- [ ] 크래시로 "처리 중"에 갇힌 키를 풀 방법(트랜잭션 또는 만료)이 있다
- [ ] 외부 호출에도 멱등 키를 전달한다
- [ ] 키의 보관 기간과 오류 응답을 문서에 공개한다
- [ ] 클라이언트는 의도마다 키를 만들고 재시도에는 같은 키를 쓴다
