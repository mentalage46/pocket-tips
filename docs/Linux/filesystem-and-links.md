# 파일 시스템과 링크

> 파일의 **이름과 내용은 별개**이고, 디스크가 차는 이유는 `ls`로 보이는 것과 다를 수 있다

[파일 권한과 프로세스](./permissions-and-processes.md)가 "누가 접근하는가"를 다뤘다면, 이 문서는 **파일이 어떻게 저장되고 연결되는가**를 다룹니다. 실행 결과는 macOS 26.5(APFS)에서 얻었고, Linux 전용 항목(`/proc` 등)은 Linux 맨페이지로 확인했습니다. 명령 옵션이 BSD와 GNU에서 다른 부분은 따로 표시했습니다.

---

## 개념 1: 파일 이름과 파일 내용(inode)은 다르다

파일 시스템은 파일의 **내용과 메타데이터**(크기, 권한, 소유자, 시각)를 **inode**라는 번호가 붙은 항목에 저장하고, 디렉터리는 **"이름 → inode 번호"** 의 목록일 뿐입니다. 즉 **이름은 inode를 가리키는 이름표**입니다.

```bash
echo "data" > a.txt
ln a.txt hard.txt          # 하드 링크: 같은 inode에 이름 하나 더
ln -s a.txt soft.txt       # 심볼릭 링크: "a.txt"라는 경로 문자열을 담은 별도 파일

ls -li a.txt hard.txt soft.txt
8168217  -rw-r--r--  2  a.txt             ← inode 8168217, 링크 수 2
8168217  -rw-r--r--  2  hard.txt          ← 같은 inode, 링크 수 2
8168220  lrwxr-xr-x  1  soft.txt -> a.txt ← 다른 inode (자기만의 파일)
```

| | 하드 링크 | 심볼릭 링크(소프트 링크) |
| --- | --- | --- |
| inode | **같음** (이름만 추가) | **다름** (경로를 담은 별도 파일) |
| 원본 삭제 시 | **데이터 유지** (링크 수가 줄 뿐) | **깨짐(dangling)** |
| 디렉터리/다른 파일 시스템 | 보통 불가 | **가능** |
| 일반적 용도 | 백업 도구의 중복 제거 등 | **설정 파일·버전 전환**(`current -> releases/v3`) |

원본을 지운 뒤의 결과입니다.

```bash
rm a.txt
cat hard.txt     # data                          ← 데이터는 살아 있음 (링크 수 2 → 1)
cat soft.txt     # No such file or directory     ← 가리키는 경로가 사라져 깨짐
```

- **`rm`은 파일을 지우는 것이 아니라 "이름을 지우는 것"** 입니다. 그 inode를 가리키는 이름이 **0개가 되고**, 그 파일을 **열고 있는 프로세스도 없을 때** 비로소 데이터가 회수됩니다.
- **심볼릭 링크의 상대 경로는 "링크가 있는 디렉터리" 기준**입니다(현재 디렉터리가 아님). `d2/` 안에서 `ln -s d1/t.txt d2/wrong`은 `d2/d1/t.txt`를 가리켜 깨지고, `ln -s ../d1/t.txt d2/right`가 맞습니다(실행 확인). 헷갈리면 **절대 경로**로 만듭니다.

### `mv`와 `cp`는 inode 관점에서 다르다

```
mv m.txt m2.txt   # inode 8168226 → 8168226  (같은 파일 시스템 안에서는 이름만 바뀜)
cp m2.txt m3.txt  # 새 inode 8168227         (내용을 복사한 새 파일)
```

- 같은 파일 시스템 안의 `mv`는 **이름(디렉터리 항목)만 바꾸므로 빠르고 원자적**입니다(대용량 파일도 순식간). 다른 파일 시스템으로 옮길 때는 복사 후 삭제라 시간이 걸립니다(일반 설명).
- 이 성질 때문에 설정 파일은 **임시 파일에 쓴 뒤 `mv`로 교체**(atomic replace)하면 읽는 쪽이 반쯤 쓰인 파일을 보지 않습니다.

## 개념 2: 삭제한 파일이 디스크를 계속 차지한다

`df`로 본 디스크 사용량과 `du`로 합산한 파일 크기가 **맞지 않을 때**의 흔한 원인입니다. 위 `rm`의 규칙 때문입니다.

```bash
exec 3< big.bin      # 프로세스(셸)가 big.bin을 열어 둠
rm big.bin           # 이름은 지웠지만 열려 있어 데이터는 남음
lsof +L1             # 링크 수가 1 미만인 열린 파일 목록
COMMAND  PID  USER  FD  TYPE  SIZE/OFF  NLINK  NODE     NAME
zsh      ...  me    3r  REG   5242880   0      8168228  /…/big.bin   ← NLINK 0, 5 MiB가 아직 점유
exec 3<&-            # 닫으면 그제야 공간 회수
```

- **로그 파일을 `rm`했는데 디스크가 줄지 않는다**면, 로그를 쓰는 프로세스가 아직 그 파일을 열고 있는 경우입니다. `lsof +L1`(링크 수 0인 열린 파일)로 찾고, 프로세스를 재시작하거나 파일을 **비우는**(`: > file`, `truncate -s 0 file`) 방식으로 처리합니다. 로그는 삭제 대신 **로테이션**([Docker 로그 회전](../Infrastructure/docker/docker-command.md#로그는-기본적으로-무한히-쌓인다))합니다.
- 출력의 `NLINK 0`이 "이름은 없는데 열려 있는 파일"의 표시입니다.

### 디스크가 찼을 때: `df` → `du`

```bash
df -h /                  # 파일 시스템별 사용량 (어느 마운트가 찼는가)
df -i /                  # inode 사용량 (공간이 남아도 inode가 다 쓰이면 파일을 못 만듦)
du -d 1 -h . | sort -h   # 어느 하위 디렉터리가 큰가 (BSD/macOS 형태)
```

- **inode도 고갈될 수 있습니다.** 작은 파일이 수백만 개 쌓이면 용량은 남아도 새 파일을 만들 수 없습니다. `df -i`의 `iused`/`ifree`로 확인합니다(macOS에서 `df -i`가 동작함을 확인).
- 하위 디렉터리별 크기: **BSD `du -d 1`**, **GNU `du --max-depth=1`**(GNU의 짧은 옵션 `-d`도 지원하지만 확인하지 않음, 미확인). 순정 macOS `du`에서 `--max-depth=1`은 `unrecognized option`이었습니다([BSD/GNU 차이](./shell-basics.md#macosbsd와-linuxgnu의-도구-차이)).
- `sort -h`는 `1K 2M 3G`처럼 **사람이 읽는 크기 단위**를 정렬합니다(macOS에서 동작 확인).
- 큰 파일 찾기: `find . -type f -size +100M`. `+1M`은 "1 MiB **초과**"라서 정확히 1 MiB인 파일은 포함되지 않았습니다(실행 확인).
- `ls -lhS`는 큰 순서로 사람이 읽는 크기를 보여 줍니다.

## 개념 3: "모든 것은 파일"과 파일 디스크립터

유닉스에서는 일반 파일뿐 아니라 장치, 파이프, 소켓도 **파일 인터페이스**로 읽고 씁니다. 열린 파일은 프로세스마다 **파일 디스크립터(fd)** 라는 정수로 접근합니다.

| fd | 이름 | 기본 연결 |
| --- | --- | --- |
| 0 | stdin | 키보드/파이프 입력 |
| 1 | stdout | 화면/파이프 출력 |
| 2 | stderr | 화면 (오류) |
| 3 이상 | 프로세스가 연 파일·소켓 | |

[리다이렉션](./shell-basics.md#리다이렉션-순서가-의미를-바꾼다)의 `2>&1`은 "fd 2를 fd 1이 가리키는 곳으로"라는 뜻입니다.

### 자주 쓰는 특수 파일

```bash
head -c 8 /dev/urandom | xxd    # 무작위 바이트
head -c 4 /dev/zero | xxd       # 0 바이트: 00000000
cmd > /dev/null                 # 출력 버리기
```

- `/dev/null`: 쓰면 사라지고 읽으면 즉시 끝, `/dev/zero`: 0 바이트의 무한 스트림, `/dev/urandom`: 무작위 바이트. 위 세 가지는 macOS에서 확인했습니다.
- **프로세스당 열 수 있는 fd 개수에는 한도가 있습니다**(`ulimit -n`). 서버가 `Too many open files`로 실패하면 연결·파일을 닫지 않는 **누수**를 먼저 의심합니다(한도 값은 이 문서에서 확인하지 않음, 미확인).

## Linux의 디렉터리 구조

Linux 맨페이지 `hier(7)`가 설명하는 전형적인 구조입니다. macOS는 `/Users`, `/System` 등 구조가 다릅니다.

| 경로 | 용도 |
| --- | --- |
| `/etc` | **이 머신에 고유한 설정 파일** |
| `/usr` | **공유 가능한 읽기 전용 데이터**. `/usr/bin`이 일반 사용자용 프로그램의 기본 위치, `/usr/lib` 라이브러리, `/usr/share` 아키텍처 독립 데이터 |
| `/usr/local` | **사이트(이 서버)에서 직접 설치한** 프로그램 (`bin`, `etc` 등) |
| `/opt` | **추가 패키지**(정적 파일) |
| `/var` | **크기가 변하는 파일**: `/var/log` 로그, `/var/lib` 프로그램 상태, `/var/cache` 캐시, `/var/spool` 대기 중인 작업(예: `/var/spool/cron`) |
| `/tmp` | **임시 파일. 예고 없이(정기 작업이나 부팅 시) 삭제될 수 있음** |
| `/run` | 부팅 이후의 실행 시 정보 |
| `/home`, `/root` | 사용자 홈, root의 홈 |
| `/srv` | 이 시스템이 **제공하는 서비스의 데이터** (웹 사이트 파일 등) |
| `/dev` | 장치 파일 |
| `/proc` | 프로세스와 커널 정보를 보여 주는 **가상 파일 시스템** (디스크에 실체가 없음) |
| `/boot` | 부트로더용 정적 파일, `/mnt` 임시 마운트 지점, `/media` 이동식 미디어 |

- **`/tmp`에 중요한 데이터를 두지 않습니다.** 예고 없이 지워질 수 있고, 모든 사용자가 쓸 수 있으므로 비밀 파일은 권한을 `600`으로 만듭니다([umask](./permissions-and-processes.md#umask-새-파일의-기본-권한은-어디서-오는가)).
- **서비스의 데이터는 `/var/lib` 또는 `/srv`**, 설정은 `/etc`, 로그는 `/var/log`로 나누면 백업과 권한 관리가 쉬워집니다. 앞의 [systemd 서비스](./services-and-scheduling.md)의 `WorkingDirectory=`/데이터 위치를 정할 때도 이 구분을 따릅니다.
- `/proc`은 Linux에서 프로세스를 점검하는 창구입니다(`/proc/<PID>/…`). macOS에는 없습니다(`hier(7)`의 설명으로 확인, 이 환경에서는 실행하지 않음).

## 🎯 체크리스트

- [ ] `rm`은 이름을 지울 뿐 — **열려 있는 파일은 공간을 계속 차지**한다는 것을 안다
- [ ] 디스크가 줄지 않으면 `lsof +L1`로 삭제된 열린 파일 확인
- [ ] 디스크가 찼을 때 `df -h` → `df -i` → `du -d 1 -h` 순서로 좁히기
- [ ] 심볼릭 링크는 상대 경로 기준이 **링크의 디렉터리**임을 기억 (헷갈리면 절대 경로)
- [ ] 설정 파일 교체는 임시 파일에 쓴 뒤 `mv`
- [ ] `/tmp`에 중요한 데이터를 두지 않기
- [ ] 로그는 삭제하지 말고 로테이션
- [ ] `Too many open files`는 fd 누수부터 의심
