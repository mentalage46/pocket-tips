# 파일 권한과 프로세스

> **누가 무엇을 할 수 있는가**(권한)와 **실행 중인 프로그램을 어떻게 다루는가**(프로세스·시그널)

[셸 스크립트의 기본](./shell-basics.md)의 종료 코드와 이어지는 내용입니다. 실행 결과는 macOS 26.5의 순정 도구(`/bin`, `/usr/bin`)에서 얻었습니다. 권한 모델과 시그널은 POSIX 공통이지만, 출력 명령(`stat`)의 옵션은 BSD와 GNU가 다릅니다.

---

## 개념 1: 권한은 "누구에게 · 무엇을" 3 × 3 으로 정한다

```
-rwxr-xr--
│└┬┘└┬┘└┬┘
│ │  │  └─ 그 밖의 사용자(other): r--  읽기만
│ │  └──── 그룹(group):         r-x  읽기, 실행
│ └─────── 소유자(user):        rwx  읽기, 쓰기, 실행
└───────── 종류: - 파일, d 디렉터리
```

| 비트 | 값 | 파일에서의 의미 | **디렉터리**에서의 의미 |
| --- | --- | --- | --- |
| `r` | 4 | 내용 읽기 | **이름 목록** 보기 (`ls`) |
| `w` | 2 | 내용 수정 | 안에 **파일 생성·삭제·이름 변경** |
| `x` | 1 | 프로그램으로 **실행** | **안으로 들어가기**, 안의 파일에 접근 |

권한은 세 자리 8진수로도 씁니다: `7`=rwx, `5`=r-x, `4`=r--. 그래서 `754`는 소유자 rwx, 그룹 r-x, 그 밖 r--입니다(실행해서 `-rwxr-xr--`임을 확인).

### chmod: 8진수와 기호

```bash
chmod 754 file           # -rwxr-xr--   (한 번에 전부 지정)
chmod u=rw,g=r,o= file   # -rw-r-----   (대상별로 지정, o=는 모든 권한 제거)
chmod g+w file           # -rw-rw----   (일부만 추가)
chmod +x script.sh       # 실행 권한 추가
```

### 디렉터리의 `r`과 `x`는 다르다

디렉터리 권한은 가장 헷갈리는 부분입니다. 파일 `dd/f`(내용 `hi`)를 두고 `dd`의 권한을 바꿔 보았습니다.

| `dd`의 권한 | `ls dd` | `cat dd/f` |
| --- | --- | --- |
| `rwxr-xr-x` (기본) | 목록 보임 | `hi` |
| **`x` 제거** (`chmod a-x dd` → `rw-r--r--`) | `ls: fts_read: Permission denied` | **`Permission denied`** |
| **`r` 제거** (`chmod a-r dd` → `-wx--x--x`) | **`ls: dd: Permission denied`** (목록 못 봄) | **`hi`** (이름을 알면 접근 가능) |

- **`x`가 없으면** 디렉터리 안으로 들어갈 수 없어 파일 이름을 알아도 접근할 수 없습니다.
- **`r`이 없고 `x`만 있으면** 목록은 못 보지만 **이름을 아는 파일은 열 수 있습니다.**
- 그래서 파일에 접근하려면 **그 경로의 모든 상위 디렉터리에 `x`** 가 있어야 합니다. 권한 오류의 상당수는 파일이 아니라 **상위 디렉터리**의 `x` 문제입니다.

### 스크립트가 "Permission denied"로 실행되지 않을 때

```bash
printf '#!/bin/sh\necho ran\n' > s.sh
./s.sh                    # permission denied   ← 실행 비트가 없음
chmod +x s.sh
./s.sh                    # ran
```

`#!`(shebang) 줄은 어떤 인터프리터로 실행할지 알려 줄 뿐, **실행 권한은 따로 필요**합니다. Git은 파일의 실행 비트(`100755`)를 추적하므로, 한 번 `chmod +x`하고 커밋하면 다른 사람도 받습니다.

## umask: 새 파일의 기본 권한은 어디서 오는가

새로 만든 파일과 디렉터리의 권한은 **기본값에서 `umask`로 지정한 비트를 뺀** 값입니다. 같은 명령을 `umask`만 바꿔 실행한 결과입니다.

| umask | 새 파일 | 새 디렉터리 | 의미 |
| --- | --- | --- | --- |
| `022` | `-rw-r--r--` (644) | `drwxr-xr-x` (755) | 그룹·타인은 쓰기 불가 (흔한 기본값) |
| `077` | `-rw-------` (600) | `drwx------` (700) | 나만 접근 (비밀 파일 생성 시) |
| `002` | `-rw-rw-r--` (664) | `drwxrwxr-x` (775) | 그룹이 함께 쓰기 (공유 디렉터리) |

- 새 **파일**은 8진수 `666`, 새 **디렉터리**는 `777`에서 시작해 `umask`를 뺍니다. 파일에 실행 비트가 처음부터 붙지 않는 이유입니다.
- 비밀(키, 토큰)을 파일로 쓸 때는 **만들 때부터 600**이 되도록 `umask 077`을 먼저 걸거나 생성 직후 `chmod 600`합니다. 만든 뒤에 `chmod`하면 그 사이에 다른 사용자가 읽을 수 있습니다. SSH 개인키 파일이 600이어야 하는 것도 같은 맥락입니다([SSH 키](../Version%20Control%20System/git/public-key.md#키-파일-권한-확인)).

### 권한을 줄 때의 원칙

- **최소 권한**: 필요한 사용자에게 필요한 만큼만. `chmod 777`은 거의 항상 잘못된 해결입니다("권한 오류가 사라졌다"는 것은 "누구나 쓸 수 있다"는 뜻).
- 웹 서버나 앱이 쓰는 디렉터리는 그 프로세스의 **실행 사용자**에게만 쓰기를 줍니다.
- 컨테이너 안에서도 root 대신 일반 사용자로 실행합니다([Dockerfile non-root](../Infrastructure/docker/docker.md#non-root-사용자-실행-보안)).

## 개념 2: 프로세스와 시그널

프로그램을 실행하면 **프로세스**가 생기고, 각 프로세스는 **PID**와 **종료 코드**를 가집니다. 프로세스에 **시그널**을 보내 종료·중단 등을 알릴 수 있습니다.

| 시그널 | 번호 | 의미 | 프로세스가 **처리(trap)** 할 수 있는가 |
| --- | --- | --- | --- |
| `SIGHUP` | 1 | 터미널 연결 끊김 (데몬은 설정 다시 읽기에 재활용) | 가능 |
| `SIGINT` | 2 | `Ctrl+C` | 가능 |
| **`SIGTERM`** | 15 | **정상 종료 요청** (`kill`의 기본값, `docker stop`의 첫 신호) | **가능** — 정리 후 종료 |
| **`SIGKILL`** | 9 | **강제 종료** | **불가능** — 커널이 즉시 종료 |

### 정상 종료(SIGTERM)와 강제 종료(SIGKILL)

실제로 비교한 결과입니다.

```bash
# SIGTERM을 처리하는 프로세스
trap 'echo "정리 후 종료"; exit 0' TERM
kill -TERM <PID>        # → "정리 후 종료", 종료 코드 0

# 처리하지 않는 프로세스
kill -TERM <PID>        # → 종료 코드 143

# SIGKILL
kill -9 <PID>           # → 종료 코드 137 (trap이 있어도 실행되지 않음)
```

- **시그널로 죽은 프로세스의 종료 코드는 `128 + 시그널 번호`** 입니다. `143 = 128 + 15`(SIGTERM), `137 = 128 + 9`(SIGKILL). 컨테이너나 CI에서 `exit code 137`이 보이면 **강제 종료(OOM killer 또는 `docker stop`의 유예 시간 초과 등)** 를 의심합니다.
- **`kill`은 먼저 `SIGTERM`(기본)** 으로 정리할 기회를 주고, 응답이 없을 때만 `kill -9`를 씁니다. `-9`는 임시 파일, 잠금, 열린 연결을 정리하지 못합니다.
- 서버는 `SIGTERM`을 받으면 **새 요청을 받지 않고, 처리 중인 요청을 마치고, 연결을 닫은 뒤** 종료해야 합니다(graceful shutdown). 이를 구현하지 않으면 배포마다 요청이 끊깁니다. `docker stop`이 `SIGTERM` 후 유예 시간(Linux 기본 10초) 뒤 `SIGKILL`을 보낸다는 점은 [Docker 명령어](../Infrastructure/docker/docker-command.md#개념-명령어-뒤의-객체와-생명주기)를 참고합니다.

### 백그라운드 실행과 기다리기

```bash
(sleep 0.3; exit 3) &      # 백그라운드로 실행, PID는 $!
wait $!                    # 끝날 때까지 기다림
echo $?                    # 3   ← wait는 자식의 종료 코드를 돌려줌
```

- `&`로 시작한 프로세스는 **터미널을 닫으면 `SIGHUP`을 받아 함께 죽을 수 있습니다.** 서버 프로세스를 이렇게 띄우지 말고 서비스 관리자(`systemd` 등)나 컨테이너로 실행합니다.
- 백그라운드 작업의 실패는 `wait`로 종료 코드를 받아야 알 수 있습니다.

### 자주 쓰는 확인 명령

```bash
ps aux | grep '[n]ode'      # 프로세스 찾기 ([n]ode는 grep 자신이 걸리지 않게 하는 관용구)
lsof -i :3000               # 3000번 포트를 쓰는 프로세스
kill <PID>                  # SIGTERM
kill -9 <PID>               # SIGKILL (마지막 수단)
```

- `lsof -i :포트`는 [포트 충돌](../Network/diagnostics.md#6-서버에서-듣고-있는가) 해결에 씁니다.
- Linux에서는 `ss -tlnp`가 같은 일을 합니다. 이 문서에서는 실행하지 않았습니다(미확인).

## 🎯 체크리스트

- [ ] 권한 문제는 파일 자체보다 **상위 디렉터리의 `x`** 부터 확인
- [ ] `chmod 777`로 해결하지 않는다 (필요한 최소 권한)
- [ ] 비밀 파일은 처음부터 `umask 077` 또는 생성 직후 `chmod 600`
- [ ] 스크립트는 shebang + 실행 비트(`chmod +x`)
- [ ] 종료는 `SIGTERM` 먼저, `kill -9`는 마지막 수단
- [ ] 서버는 `SIGTERM`을 처리해 정상 종료
- [ ] 종료 코드 `143` = SIGTERM, `137` = SIGKILL
- [ ] 서버를 `&`로 띄우지 않고 서비스 관리자·컨테이너 사용
