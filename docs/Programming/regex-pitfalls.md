# 정규식의 함정

> 짧은 패턴 하나가 **서버 전체를 몇 초간 멈추게** 할 수 있고, 같은 패턴이 Unicode·플래그에 따라 다르게 동작한다

정규식은 편리하지만 직관과 다르게 동작하는 지점이 많습니다. 이 문서는 JavaScript(V8) 기준으로 **느려지는 경우(ReDoS)** 와 **틀린 결과를 내는 경우**를 직접 실행한 결과로 정리합니다.

> **모든 수치와 출력은 Node 24.13(V8 13.6)에서 직접 실행한 결과입니다.** 시간은 이 기기의 측정값이라 환경마다 다릅니다. 다른 엔진(PCRE, Python `re`, Java 등)은 백트래킹 방식이면 비슷한 문제가 있지만 이 문서에서 실행하지 않았습니다.

---

## 파국적 백트래킹(ReDoS)

### 왜 느려지는가

JavaScript의 정규식 엔진은 **백트래킹**으로 동작합니다. 선택지가 있을 때 하나를 시도하고, 뒤에서 실패하면 돌아와 다른 경로를 시도합니다. 패턴에 **중첩된 반복**(`(a+)+`)이 있으면 같은 문자열을 나누는 방법의 수가 지수적으로 늘고, **실패하는 입력**에서는 그 경우를 전부 시도한 뒤에야 "불일치"로 결론 내립니다.

```js
const evil = /^(a+)+$/;
evil.test('a'.repeat(n) + 'b');      // 끝의 b 때문에 반드시 실패
```

| n (a의 개수) | 실패를 확인하는 데 걸린 시간 |
| --- | --- |
| 24 | 108ms |
| 26 | 434ms |
| **28** | **1,729ms** |

n이 2 늘 때마다 시간이 약 **4배**, 즉 글자 하나당 2배입니다. 이 추세를 그대로 연장하면 n=36 근처에서 수 분이 걸리지만, 그 길이는 실행하지 않았습니다(외삽). 반대로 **일치하는 입력**(`'a'.repeat(5000)`)은 0ms였습니다. 평소 테스트(정상 입력)에서는 전혀 드러나지 않다가 **공격자가 만든 입력 한 줄**에서 터지는 이유입니다.

### 실전에서 만나는 모양

```js
const email = /^([a-zA-Z0-9]+\.?)+@example\.com$/;
email.test('a'.repeat(n) + '!');
```

| n | 걸린 시간 |
| --- | --- |
| 30 | 72ms |
| 33 | 166ms |
| 36 | 1,333ms |
| **39** | **10,682ms (약 10.7초)** |

이메일 검증에서 흔히 쓰는 모양(`[...]+`와 선택적 `\.?`을 그룹으로 묶고 `+` 반복)입니다. 39글자 입력 하나가 **10초 넘게 CPU를 점유**했습니다. 정규식 실행은 동기 코드라서, Node 서버에서는 그동안 **다른 모든 요청이 멈춥니다**([이벤트 루프가 막히는 이유](./async-and-event-loop.md#개념-2-동기-코드가-이벤트-루프를-막는다)). `AbortSignal`이나 `Promise.race` 타임아웃으로도 중단할 수 없습니다.

### 위험한 패턴의 특징

- **중첩된 반복**: `(a+)+`, `(a*)*`, `(a|aa)+`
- **겹치는 선택지의 반복**: `(a|a)+`, `(\w|\d)+`처럼 같은 문자를 두 경로가 모두 받아들임
- **반복 + 반복이 같은 문자를 소비**하는 연속: `\d+\d+`, `.*.*` (다항식이지만 입력이 크면 느림)
- 사용자 입력이 **정규식 패턴 자체**가 되는 경우(`new RegExp(userInput)`)

### 고치는 방법

1. **겹치지 않게 다시 쓴다.** 위 이메일형은 "구분자로 이어진 토큰"으로 바꾸면 한 문자를 받는 경로가 하나뿐이라 안전합니다.

```js
const email2 = /^[a-zA-Z0-9]+(\.[a-zA-Z0-9]+)*@example\.com$/;
email2.test('a'.repeat(100000) + '!');     // 0ms (10만 글자)
/^a+$/.test('a'.repeat(1_000_000) + 'b');  // 3ms (100만 글자)
```

2. **입력 길이를 먼저 제한한다.** 아무리 나쁜 패턴도 입력이 짧으면 못 커집니다. 이메일은 길이 상한이 있으니 정규식 전에 `s.length <= 254` 등을 확인합니다.
3. **정규식으로 하지 않는다.** 이메일 형식 전체를 정규식으로 검증하려고 하지 말고, 최소한(`@` 하나, 공백 없음)만 검사한 뒤 **확인 메일**로 실제 소유를 검증하는 편이 정확합니다.
4. **선형 시간 엔진을 쓴다**(아래).

### V8의 선형 시간 엔진 (실험 기능)

V8에는 입력 길이에 비례한 시간을 보장하는 **비백트래킹 엔진**이 실험 기능으로 있습니다(V8 블로그). Node에서 실행 플래그로 켭니다.

| 플래그 | 동작 | 직접 확인 |
| --- | --- | --- |
| `--enable-experimental-regexp-engine-on-excessive-backtracks` | 백트래킹이 과도해지면(기본 50,000회) 비백트래킹 엔진으로 **자동 전환** | `/^(a+)+$/`, n=40 → **0ms** (플래그 없이 같은 코드는 60초 안에 끝나지 않아 중단) |
| `--enable-experimental-regexp-engine` | 비표준 **`l` 플래그**를 인식. `l` 정규식은 항상 새 엔진으로 실행 | `new RegExp('^(a+)+$', 'l')`, n=40 → 0ms |

- 자동 전환은 **역참조, 전방/후방 탐색, 큰 반복 횟수(`a{200,500}`), `u`·`i` 플래그**가 있는 정규식에는 적용되지 않는다고 V8 블로그가 밝힙니다. 이 문서에서는 이 제외 조건을 개별로 실험하지 않았습니다.
- `l` 플래그가 붙은 정규식에서 선형 시간을 보장할 수 없는 기능을 쓰면 **생성 시점에 예외**가 납니다. 역참조 `^(a)\1$`는 `Cannot be executed in linear time`이었습니다.
- 둘 다 **비표준 실험 기능**이고 실행 플래그를 서버에 전달해야 하므로, 이를 믿고 위험한 패턴을 방치하지 않습니다. 다른 런타임(브라우저, Deno, Bun)에서의 지원은 확인하지 않았습니다.

## 틀린 결과를 내는 함정

### `g`(또는 `y`) 플래그와 `test()`는 상태를 가진다

```js
const g = /a/g;
g.test('a'); g.test('a'); g.test('a');   // true, false, true
g.lastIndex;                              // 1
```

`g` 플래그가 있는 정규식은 `lastIndex`를 기억해서 같은 문자열에 `test`를 반복하면 **결과가 번갈아 바뀝니다.** 모듈 최상위에 `g` 정규식을 두고 `test`로 검사하는 코드가 간헐적으로 실패하는 흔한 원인입니다. 검사만 할 때는 `g`를 빼거나, `String.prototype.match`/`matchAll`을 씁니다.

### `.`, `^`, `$`와 줄바꿈

| 코드 | 결과 |
| --- | --- |
| `/a.b/.test('a\nb')` | `false` — `.`은 줄바꿈과 일치하지 않음 |
| `/a.b/s.test('a\nb')` | `true` — `s`(dotAll) 플래그 |
| `'x\ny'.match(/^y/)` | `null` — `^`는 기본적으로 문자열 시작만 |
| `'x\ny'.match(/^y/m)?.index` | `2` — `m` 플래그에서 줄 시작 |

### `\w`와 `\b`는 한글을 단어 문자로 보지 않는다

```js
/\w/.test('한');          // false  (\w = [A-Za-z0-9_])
/\p{L}/u.test('한');      // true   (유니코드 글자, u 플래그 필요)
/\b한\b/.test('한');      // false  (\b 도 \w 기준)
```

한글·일본어 등이 들어올 수 있는 입력에서 `\w+`로 검증하면 **정상 입력을 거부**합니다. 문자 종류는 `\p{L}`, `\p{N}` 같은 **유니코드 속성**(+`u` 플래그)으로 지정합니다.

### 이모지와 `u` 플래그

```js
'😀'.length;               // 2   (UTF-16 코드 유닛 2개)
[...'😀'].length;          // 1
/^.$/.test('😀');          // false
/^.$/u.test('😀');         // true
```

`u` 플래그가 없으면 `.`이 코드 유닛 하나만 받아서 이모지 같은 보조 평면 문자가 두 글자로 취급됩니다. 문자 수를 세는 문제는 [i18n 문서](../I18N/README.md)와도 맞닿아 있습니다. `u` 플래그를 쓰면 일부 이스케이프가 더 엄격해져 기존 패턴이 `SyntaxError`가 될 수 있으니 적용 후 테스트합니다(이 문서에서는 확인하지 않음).

### 탐욕적 vs 게으른 수량자

```js
const html = '<b>one</b><b>two</b>';
html.match(/<b>.*<\/b>/)[0];    // '<b>one</b><b>two</b>'  (탐욕: 가장 길게)
html.match(/<b>.*?<\/b>/)[0];   // '<b>one</b>'            (게으른: 가장 짧게)
```

게으른 수량자가 일부 문제를 해결하지만 **HTML 같은 중첩 구조는 정규식으로 파싱하지 않습니다.** 파서를 씁니다.

### `replace`의 특수 치환 문자열

```js
'cost'.replace(/cost/, '$&!');          // 'cost!'   ($& = 일치한 전체)
'cost'.replace(/cost/, () => '$&!');    // '$&!'     (함수 반환값은 그대로)
```

치환 문자열에 **사용자 입력**을 넣으면 `$&`, `$1`, `` $` `` 같은 패턴이 해석됩니다. 입력을 그대로 치환하려면 함수 형태로 반환합니다.

### 사용자 입력을 패턴에 넣을 때는 이스케이프

```js
const user = 'a.b*c';
new RegExp(user).test('aXbbbc');                       // true  (. 와 * 이 메타문자로 해석됨)
new RegExp(user.replace(/[.*+?^${}()|[\]\\]/g, '\\$&'))
  .test('aXbbbc');                                     // false (글자 그대로)
RegExp.escape(user);                                   // '\x61\.b\*c'
```

Node 24.13에는 `RegExp.escape()`가 있었고 위 결과를 돌려줬습니다. 첫 글자 `a`가 `\x61`로 바뀐 것은 정상 동작입니다(맨 앞의 영숫자를 이스케이프해서 앞 토큰과 합쳐지는 문제를 막으려는 것으로 보이며, 정확한 규칙은 확인하지 않음). 지원하지 않는 환경에서는 위처럼 직접 이스케이프합니다.

## 🎯 체크리스트

- [ ] 중첩된 반복(`(a+)+`)과 겹치는 선택지의 반복이 없는지 확인한다
- [ ] **실패하는** 긴 입력(예: 일치 직전에 틀리는 40~50자)으로도 시간을 재 본다
- [ ] 사용자 입력에는 **길이 상한**을 먼저 건다
- [ ] 사용자 입력을 `new RegExp()`에 넣을 때는 이스케이프(`RegExp.escape`)한다
- [ ] 이메일·URL 같은 복잡한 형식은 정규식 전체 검증 대신 최소 검사 + 실제 확인으로 대체한다
- [ ] `g`/`y` 플래그가 있는 정규식에 `test`를 반복해서 쓰지 않는다
- [ ] 한글 등 비ASCII 입력이 가능하면 `\w` 대신 `\p{L}` + `u` 플래그를 쓴다
- [ ] 줄바꿈이 있을 수 있으면 `s`/`m` 플래그를 의도에 맞게 쓴다
- [ ] HTML/JSON 같은 구조 데이터는 정규식 대신 파서를 쓴다
- [ ] `replace`에 사용자 입력을 넣을 때는 함수 형태로 반환한다
- [ ] 정규식 폭주 위험이 큰 서비스는 선형 시간 엔진(실험) 또는 별도 프로세스/Worker 분리를 검토한다
