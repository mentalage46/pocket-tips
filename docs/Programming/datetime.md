# 시간과 타임존

> "지금", "오늘", "내일 오전 9시"가 **서로 다른 개념**이라는 것을 이해하고 버그를 피하기

[로그 시각](../Observability/logging.md), [인증서 만료](../Network/tls.md), [쿠키 만료](../Security/cookie.md), [레이트 리밋 윈도우](../API/rate-limiting.md)에서 시간이 계속 등장하지만 한곳에 정리된 적이 없었습니다. 이 문서의 실행 결과는 Node.js 24.13(`Intl`)에서 얻었습니다.

---

## 개념 1: 시간에는 세 가지 종류가 있다

| 종류 | 질문 | 예 | 저장 방법 |
| --- | --- | --- | --- |
| **순간(instant)** | 지구 어디서나 같은 **한 시점**은? | 주문이 생성된 시각, 로그 시각, 토큰 만료 시각 | **UTC** (또는 오프셋이 포함된 ISO 8601, epoch) |
| **달력 날짜/시계 시각** | 사람이 벽시계/달력으로 읽는 값 | 생일 `1990-05-01`, 영업 시작 `09:00` | 날짜/시각 + (필요하면) **타임존 이름** |
| **기간(duration)** | 얼마나 걸렸나 | 30분, 3일 | 초/밀리초 (달력 단위의 "1개월"은 길이가 다름) |

많은 버그가 이 셋을 하나의 `Date` 객체로 뭉뚱그릴 때 생깁니다. "주문 시각"은 순간이고, "생일"은 시간대와 무관한 달력 날짜이며, "매주 월요일 09:00 회의"는 **서울 시간으로 읽는 시계 시각**입니다.

### `Date`는 "순간"이고 타임존이 없다

MDN의 설명: JavaScript `Date`는 epoch 이후 경과한 밀리초이며 **타임존과 무관하게 한 순간을 정의**합니다. 타임존은 `Date`에 저장되지 않고, `getHours()`나 `toString()`처럼 구성 요소를 읽거나 서식화할 때 **실행 환경(사용자 기기)의 설정**으로 적용됩니다.

같은 `Date`를 여러 지역에서 읽은 결과입니다(`2026-10-22T00:00:00Z`).

| 타임존 | 표시 |
| --- | --- |
| UTC | 2026-10-22 00:00 |
| Asia/Seoul | 2026-10-22 09:00 (UTC+9) |
| America/New_York | **2026-10-21** 20:00 (UTC−4) |
| Asia/Kolkata | 2026-10-22 05:30 (UTC+5:30) |
| Asia/Kathmandu | 2026-10-22 05:45 (UTC+5:45) |

- 같은 순간이 지역에 따라 **다른 날짜**가 될 수 있습니다(뉴욕은 21일).
- 오프셋이 **정시 단위가 아닌** 지역이 있으므로 "시간대 = 정수 시간 차이"로 가정하면 안 됩니다.

## 개념 2: 문자열을 읽는 규칙이 환경에 따라 달라진다

JavaScript의 가장 흔한 함정입니다. 오프셋이 없는 문자열은 **형태에 따라 다르게** 해석됩니다(MDN, ECMAScript).

| 문자열 | 해석 |
| --- | --- |
| `"2026-10-22"` (날짜만) | **UTC 자정** |
| `"2026-10-22T00:00:00"` (시각 포함, 오프셋 없음) | **로컬 시간** (실행 환경의 타임존) |
| `"2026-10-22T00:00:00Z"` 또는 `+09:00` | 명확함 |

세 타임존에서 같은 코드를 실행한 결과입니다.

```
TZ=Asia/Seoul          date-only: 2026-10-22T00:00Z   local-no-offset: 2026-10-21T15:00Z   withZ: 2026-10-22T00:00Z
TZ=America/Los_Angeles date-only: 2026-10-22T00:00Z   local-no-offset: 2026-10-22T07:00Z   withZ: 2026-10-22T00:00Z
TZ=UTC                 date-only: 2026-10-22T00:00Z   local-no-offset: 2026-10-22T00:00Z   withZ: 2026-10-22T00:00Z
```

- `"2026-10-22T00:00:00"`는 **서버(보통 UTC)와 개발자 노트북(서울)에서 다른 순간**이 됩니다. "내 컴퓨터에서는 되는데 서버에서는 하루 어긋난다"의 전형적인 원인입니다.
- 날짜만 있는 문자열은 UTC로 해석되므로, 로스앤젤레스에서 `getDate()`를 읽으면 **21일**이 나옵니다(실행 확인). 달력 날짜(생일 등)는 `Date`로 표현하지 않는 것이 안전합니다.
- **서버 사이에서 주고받는 문자열은 항상 `Z`나 오프셋을 포함**합니다.

그 밖의 `Date` 함정:

- **월이 0부터** 시작합니다. `new Date(2026, 9, 22)`가 10월 22일이고 `getMonth()`는 `9`를 돌려줍니다. 문자열의 `MM`은 `01`~`12`입니다.
- **가변(mutable)** 입니다. `d.setDate(...)`는 같은 객체를 바꿔서, 다른 곳이 참조하던 값이 함께 바뀝니다(`const e = d; e.setDate(...)` 후 `d`도 바뀜을 확인).

## 개념 3: 서머타임(DST)이 있으면 "하루"와 "24시간"이 다르다

서머타임 지역(예: 미국 동부)에서는 **하루의 길이가 23시간 또는 25시간**인 날이 있습니다. 뉴욕에서 실행한 결과입니다.

```
2026-03-07 12:00 EST  + 24시간  →  2026-03-08 13:00 EDT     ← 시계는 13:00 (12:00이 아님)

2026-03-08 달력 하루의 길이: 23시간   (봄에 한 시간 건너뜀)
2026-11-01 달력 하루의 길이: 25시간   (가을에 한 시간 반복)
```

| 현상 | 설명 | 예 |
| --- | --- | --- |
| **존재하지 않는 시각** (봄) | 시계가 02:00에서 03:00으로 건너뜀. `2026-03-08 02:30`은 뉴욕에 없음 | `new Date(2026, 2, 8, 2, 30)`이 **03:30 EDT**로 조용히 밀림 |
| **두 번 있는 시각** (가을) | 01:00~02:00이 두 번 반복됨. `2026-11-01 01:30`이 모호 | `01:30 EDT`(05:30Z)와 `01:30 EST`(06:30Z)가 **60분 차이** |

- "다음 날 같은 시각"을 구하려고 **밀리초에 24시간을 더하면** 서머타임 날에 시계 시각이 어긋납니다. 달력 연산(`1일 후`)이 필요하면 **타임존을 인식하는 달력 API**(Temporal, Luxon 등)로 계산합니다.
- 서머타임이 없는 지역(`UTC`)의 서버에서만 테스트하면 이 문제를 놓칩니다. **서머타임 경계 날짜**를 테스트에 넣습니다.

## 타임존은 "오프셋"이 아니라 "지역 규칙"이다

| 표기 | 예 | 담고 있는 정보 |
| --- | --- | --- |
| **오프셋** | `+09:00`, `-04:00` | 그 순간의 UTC와의 차이만. 규칙은 모름 |
| **타임존 이름 (IANA)** | `Asia/Seoul`, `America/New_York` | **그 지역의 오프셋 변경 이력과 서머타임 규칙** |

- `-04:00`만 저장하면 "이 시각 이후 6개월 뒤"가 `-04:00`일지 `-05:00`일지 알 수 없습니다.
- 타임존 규칙은 **정치적 결정으로 바뀝니다.** 규칙 데이터베이스(IANA tz database)는 계속 갱신되므로, 런타임·OS·라이브러리의 타임존 데이터가 오래되면 결과가 틀립니다. 이 환경의 Node는 tz 데이터 `2025b`(ICU 77.1)를 담고 있었습니다.

### 무엇을 저장할 것인가

| 사건의 성격 | 저장 | 이유 |
| --- | --- | --- |
| **이미 일어난 일** (주문 생성, 로그, 결제) | **UTC 순간** | 한 시점이 확정됨. 표시할 때만 변환 |
| **미래의 시계 시각** ("서울 시간 내일 09:00 회의", 반복 일정) | **로컬 날짜·시각 + IANA 타임존 이름** | 규칙이 바뀌면 UTC로 환산한 값이 틀어질 수 있음. 약속은 "그 지역의 09:00" |
| **달력 날짜** (생일, 마감일) | `date` 타입 (`YYYY-MM-DD`) | 시간대와 무관 |

## 데이터베이스에서

### PostgreSQL

| 타입 | 동작 |
| --- | --- |
| `timestamp with time zone` (`timestamptz`) | 입력을 **UTC로 변환해 저장**. 출력은 **세션의 `TimeZone` 설정으로 변환**해 표시. 입력된 원래 타임존은 **보존되지 않음** |
| `timestamp without time zone` | 타임존 표시를 **조용히 무시**. 입력된 날짜/시각 필드를 그대로 저장 |

```sql
SET TIME ZONE 'America/New_York';
SELECT TIMESTAMP '2004-10-19 10:23:54+02';                    -- 2004-10-19 10:23:54   (오프셋이 무시됨!)
SELECT TIMESTAMP WITH TIME ZONE '2004-10-19 10:23:54+02';     -- 2004-10-19 04:23:54-04 (UTC 08:23:54로 저장)
```

- PostgreSQL은 리터럴 문자열의 내용을 보고 타입을 정하지 않으므로, 타입을 명시하지 않은 `TIMESTAMP '...+02'`는 **오프셋이 있어도 무시**됩니다.
- 문서는 타임존을 쓸 때 날짜와 시각이 함께 있는 타입을 권하고 **`time with time zone`은 권하지 않습니다.**
- 순간을 저장하는 컬럼은 대개 `timestamptz`가 맞습니다(문서의 문장은 "순간이 중요할 때"의 선택으로 이해).

### MySQL

| 타입 | 범위 | 동작 |
| --- | --- | --- |
| `DATETIME` | `1000-01-01` ~ `9999-12-31` | 타임존 변환 **없음** (넣은 그대로) |
| `TIMESTAMP` | `1970-01-01 00:00:01` UTC ~ **`2038-01-19 03:14:07` UTC** | 현재 연결의 타임존에서 **UTC로 변환해 저장**, 조회 시 다시 변환 |

- `TIMESTAMP`의 상한 `2038-01-19 03:14:07`은 부호 있는 32비트 초(`2^31 − 1`초)의 한계와 같은 값입니다(`new Date((2**31-1)*1000)`이 `2038-01-19T03:14:07.000Z`). **2038년 문제**입니다.
- 저장과 조회 사이에 연결 타임존을 바꾸면 `TIMESTAMP` 값이 달라 보입니다. 연결/서버 타임존을 **UTC로 통일**하는 것이 안전합니다.

## 서로 시간을 주고받을 때: 형식

| 형식 | 예 | 쓰는 곳 |
| --- | --- | --- |
| **RFC 3339 / ISO 8601** | `2026-10-22T09:00:00+09:00`, `2026-10-22T00:00:00Z` | **API 본문, 로그, DB 입출력 (기본 선택)** |
| **epoch** | `1792655412` (초), `1792655412000` (밀리초) | JWT `exp`/`iat`(초), 내부 계산. **단위(초/밀리초)를 문서에 명시** |
| **HTTP-date** | `Sun, 06 Nov 1994 08:49:37 GMT` | `Last-Modified`, `Retry-After`, `Expires` 같은 HTTP 헤더 ([HTTP 캐싱](../Network/http-caching.md)) |

- RFC 3339(2002)는 인터넷에서 쓰는 타임스탬프 형식으로, ISO 8601의 프로필입니다. `Z`는 UTC를 뜻합니다.
- HTTP-date의 선호 형식(IMF-fixdate)은 **고정 길이이고 항상 GMT 한 가지 영역**입니다.
- 초 단위와 밀리초 단위를 섞어 쓰는 실수가 흔합니다. JWT의 `exp`는 **초**이고 JavaScript의 `Date.now()`는 **밀리초**입니다([JWT](../Security/jwt.md#클레임claims-정리)).

## 기간 측정: 시계가 아니라 단조 시계를 쓴다

**벽시계(`Date.now()`)** 는 NTP 동기화나 관리자의 시간 변경으로 **뒤로 가거나 건너뛸 수 있습니다.** 걸린 시간(duration)을 재거나 타임아웃을 구현할 때는 **단조 증가하는 시계**(`performance.now()`, 언어별 monotonic clock)를 씁니다. Redis의 TTL이 벽시계를 쓰기 때문에 시간 변경이 락 안전성에 영향을 준다는 공식 문서의 경고도 같은 문제입니다([Redis 분산 락](../Data/caching/redis.md#thundering-herd-방지)).

## 도구 선택

- `Date`는 위 이유들로 **레거시**로 간주됩니다. MDN은 `Temporal` API가 도입되었으므로 새 코드에는 `Temporal`을 고려하라고 안내하지만, 같은 문서가 **아직 모든 주요 브라우저에서 쓸 수 있는 기능(Baseline)이 아니라고** 밝힙니다. Node 24.13에서도 기본으로는 `typeof Temporal`이 `undefined`였고, `--harmony-temporal` 플래그를 주면 `object`였습니다. 쓰려는 환경의 지원 여부를 먼저 확인합니다.
- Moment.js는 공식 문서가 **"유지보수 모드의 레거시 프로젝트"** 라고 밝히므로 새 프로젝트에는 다른 선택지를 검토합니다. (대안 라이브러리의 현황은 이 문서에서 확인하지 않았습니다. 미확인)
- 표시와 서식화는 **`Intl.DateTimeFormat`** 이 내장으로 처리합니다. 타임존과 로케일을 지정하면 서머타임도 적용합니다([I18N: 날짜·숫자 포맷](../I18N/translation.md#날짜숫자통화정렬은-직접-만들지-않고-intl을-쓴다)).

```javascript
new Intl.DateTimeFormat("ko-KR", { timeZone: "Asia/Seoul", dateStyle: "medium", timeStyle: "short" }).format(date);
```

## 🎯 체크리스트

- [ ] **순간**은 UTC로 저장·전송, 표시할 때만 사용자 타임존으로 변환
- [ ] 주고받는 문자열은 `Z` 또는 오프셋 포함 (RFC 3339 / ISO 8601)
- [ ] 오프셋 없는 `"YYYY-MM-DDTHH:mm:ss"`를 `new Date()`에 넣지 않음
- [ ] 미래의 시계 시각(회의, 반복 일정)은 **IANA 타임존 이름**과 함께 저장
- [ ] 달력 날짜(생일, 마감일)는 `date` 타입
- [ ] DB 서버·연결 타임존 UTC로 통일, PostgreSQL은 `timestamptz`, MySQL `TIMESTAMP`의 2038 한계 인지
- [ ] "하루 후"를 `+24시간`으로 계산하지 않음, 서머타임 경계 날짜를 테스트에 포함
- [ ] 기간 측정은 단조 시계 (`performance.now()`)
- [ ] 초와 밀리초 단위 구분 (JWT `exp`는 초)
- [ ] 런타임·OS의 타임존 데이터 갱신 확인
