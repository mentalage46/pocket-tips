# IEC 61131-3 개요

IEC 61131-3은 PLC 프로그래밍 언어와 프로그램 구조를 정한 국제 표준입니다. 제조사마다 편집기와 주소 체계는 다르지만, 대부분의 PLC 도구가 이 표준의 언어·데이터 타입·POU 개념을 따르거나 비슷하게 구현합니다. 표준을 알면 처음 보는 제조사 도구도 빨리 읽을 수 있습니다.

먼저 알면 좋은 개념: [PLC 구성](../basics/plc-architecture.md), [스캔 사이클](../basics/scan-cycle.md)

## 판(edition) 역사

| 판 | 발행 | 주요 변화 |
| --- | --- | --- |
| 1판 | 1993 | 최초 발행. 5개 언어(IL, ST, LD, FBD, SFC)와 POU·데이터 타입 정의 |
| 2판 | 2003 | 1판 개정 |
| 3판 | 2013-02-20 | 2판과 호환되는 확장. 새 데이터 타입과 변환 함수, 참조(reference), 네임스페이스, 클래스·기능 블록의 객체지향(OOP) 기능 |
| 4판 | 2025-05-22 | UTF-8 문자열과 관련 함수 추가. 2013판 대비 추가·삭제·폐기 기능 목록은 부속서 B에 정리 |

- IL(Instruction List)은 3판에서 폐기 예정(deprecated)으로 지정되고 4판에서 삭제되었다고 알려져 있습니다. IEC 공식 요약에는 "부속서 B에 추가·삭제·폐기 목록이 있다"고만 적혀 있고, 부속서 B 원문은 유료라 직접 확인하지 못했습니다(IL 삭제는 2차 출처 기준).
- 4판의 UTF-8 문자 타입으로 `UCHAR`, `USTRING`이 소개됩니다(2차 출처 기준).
- 표준이 바뀌어도 제조사 도구가 바로 따라가지는 않습니다. 실제로 쓸 수 있는 기능은 사용하는 도구의 매뉴얼로 확인합니다. IL도 하위 호환을 위해 계속 지원하는 도구가 있습니다.

## 5개 언어 비교

| 언어 | 형태 | 표현 방식 | 강점 | 약점 |
| --- | --- | --- | --- | --- |
| LD (Ladder Diagram) | 그래픽 | 릴레이 회로처럼 접점·코일을 렁(rung)으로 배치 | 전기 기술자가 읽기 쉬움, 온라인 모니터링이 직관적 | 계산·반복·데이터 처리가 길어짐 |
| FBD (Function Block Diagram) | 그래픽 | 블록을 선으로 연결한 신호 흐름 | 아날로그·PID·연속 제어 흐름이 잘 보임 | 분기·순서 제어가 복잡해지면 선이 얽힘 |
| ST (Structured Text) | 텍스트 | Pascal 계열 고급 언어(`IF`, `CASE`, `FOR`) | 계산, 배열, 문자열, 상태 머신, 텍스트 diff | 현장 보전 인력에게 낯설 수 있음 |
| SFC (Sequential Function Chart) | 그래픽 구조 | 스텝·전이·액션으로 순서를 그림 | 공정 순서와 현재 단계가 한눈에 보임 | 작은 로직에는 과함, 도구별 구현 차이 큼 |
| IL (Instruction List) | 텍스트 | 어셈블리와 비슷한 누산기 명령 | 과거 코드 호환 | 3판 폐기 예정, 4판 삭제(위 참고). 새 코드에 쓰지 않음 |

SFC는 단독 언어라기보다 프로그램을 스텝으로 나누는 구조이고, 각 스텝의 액션과 전이 조건은 다른 언어(LD·ST 등)로 작성합니다.

### 언제 무엇을 쓰나 (경험칙)

| 상황 | 추천 |
| --- | --- |
| 인터록, 단순 on/off, 현장 보전 인력이 자주 보는 로직 | LD |
| 아날로그 스케일링, PID, 신호 흐름이 중요한 로직 | FBD |
| 계산, 배열·레시피 처리, 통신 데이터 파싱, 상태 머신 | ST |
| 여러 단계로 이루어진 공정 순서 | SFC 또는 ST의 `CASE` 상태 머신([시퀀스 패턴](./sequence-patterns.md)) |

한 프로젝트 안에서 언어를 섞어도 됩니다. 보통 재사용 기능 블록은 ST로, 상위 호출과 인터록은 LD로 작성합니다. 팀 안에서 "어떤 종류의 로직은 어떤 언어로"를 정해 두면 유지보수가 쉬워집니다.

## POU (Program Organization Unit)

POU는 프로그램을 이루는 기본 단위입니다.

| POU | 내부 상태 | 인스턴스 | 용도 | 예 |
| --- | --- | --- | --- | --- |
| `FUNCTION` | 없음. 같은 입력이면 같은 출력 | 없음 | 계산, 변환 | 스케일 변환, 최댓값 |
| `FUNCTION_BLOCK` | 있음. 호출 사이에 값 유지 | 있음. 인스턴스마다 메모리 분리 | 장치·기능 단위 재사용 | 타이머(TON), 모터, 밸브 |
| `PROGRAM` | 있음 | 태스크에 연결되어 실행 | 최상위 제어 로직 | 컨베이어 라인 제어 |

기능 블록은 클래스, 인스턴스는 객체와 비슷하게 생각하면 됩니다. 모터 10대에는 `FB_Motor` 하나를 만들고 인스턴스 10개를 선언합니다.

3판에서 추가된 OOP 기능(`METHOD`, `INTERFACE`, `EXTENDS`, `IMPLEMENTS` 등)은 CODESYS·TwinCAT 계열처럼 지원하는 도구와 그렇지 않은 도구가 있습니다. 상속을 깊게 쓰면 현장에서 추적하기 어려우므로 인터페이스와 조합 위주로 씁니다(경험칙).

## 구성·리소스·태스크

표준의 소프트웨어 모델은 아래처럼 계층을 이룹니다.

```text
CONFIGURATION (PLC 전체)
└── RESOURCE (CPU 하나에 해당)
    ├── TASK  Fast   (주기 2ms, 우선순위 높음)  → PROGRAM 인스턴스: Motion
    ├── TASK  Main   (주기 10ms)               → PROGRAM 인스턴스: Line, Alarm
    └── TASK  Event  (입력 상승 시 1회)          → PROGRAM 인스턴스: Capture
```

| 요소 | 의미 |
| --- | --- |
| 구성(Configuration) | PLC 시스템 전체. 전역 변수와 리소스를 담음 |
| 리소스(Resource) | 프로그램을 실행하는 처리 단위. 보통 CPU 하나 |
| 태스크(Task) | 실행 조건. 주기(cyclic) 또는 이벤트로 시작하고 우선순위를 가짐 |
| 프로그램 인스턴스 | 태스크에 연결되어 실제로 실행되는 PROGRAM |

태스크 주기와 우선순위는 응답 시간과 직결됩니다. 빠른 처리가 필요한 로직만 빠른 태스크에 두고, 태스크 사이에서 공유하는 변수는 한쪽에서만 쓰도록 정합니다. 자세한 내용은 [스캔 사이클](../basics/scan-cycle.md)을 참고합니다.

## 데이터 타입

| 분류 | 타입 | 크기·범위 | 리터럴 예 |
| --- | --- | --- | --- |
| 논리 | `BOOL` | 1비트(TRUE/FALSE) | `TRUE`, `0` |
| 비트열 | `BYTE`, `WORD`, `DWORD`, `LWORD` | 8/16/32/64비트 | `16#FF`, `2#1010` |
| 부호 있는 정수 | `SINT`, `INT`, `DINT`, `LINT` | 8/16/32/64비트. `INT`는 -32768~32767 | `-100` |
| 부호 없는 정수 | `USINT`, `UINT`, `UDINT`, `ULINT` | 8/16/32/64비트 | `65535` |
| 실수 | `REAL`, `LREAL` | 32/64비트 부동소수점 | `1.5`, `1.0E3` |
| 시간 | `TIME` | 경과 시간 | `T#500MS`, `T#1M30S` |
| 날짜·시각 | `DATE`, `TIME_OF_DAY`, `DATE_AND_TIME` | 달력 날짜·시각 | `D#2026-10-21` |
| 문자열 | `STRING`, `WSTRING` | 1바이트 / 2바이트 문자 | `'abc'`, `"abc"` |
| 사용자 정의 | `STRUCT`, `ARRAY`, 열거형(ENUM) | 조합 | 아래 예 |

```text
TYPE E_Mode : (MANUAL, AUTO, HOMING); END_TYPE

TYPE ST_Recipe :
STRUCT
    sName      : STRING(20);
    rTempSet   : REAL;          (* 설정 온도 [°C] *)
    tHoldTime  : TIME;
END_STRUCT
END_TYPE

VAR
    eMode      : E_Mode := MANUAL;
    aRecipes   : ARRAY[1..10] OF ST_Recipe;
END_VAR
```

- 카운터·누적값처럼 커질 수 있는 값은 `INT`(최대 32767) 대신 `DINT`를 씁니다. 16비트 오버플로는 흔한 현장 버그입니다.
- `REAL` 값을 `=`로 비교하지 않습니다. 허용 오차 범위로 비교합니다.
- 실제 지원 타입과 크기는 제조사마다 다르므로 매뉴얼을 확인합니다. 예를 들어 CODESYS 표준 라이브러리의 카운터 `PV`·`CV`는 `WORD` 타입입니다.

## 변수 섹션

| 섹션 | 의미 | 주로 쓰는 곳 |
| --- | --- | --- |
| `VAR` | 내부 변수. 인스턴스 안에서 값 유지 | FB, PROGRAM |
| `VAR_INPUT` | 입력. 호출하는 쪽이 값을 넣음 | FUNCTION, FB |
| `VAR_OUTPUT` | 출력. 호출 후 읽음 | FB |
| `VAR_IN_OUT` | 참조로 전달. 호출 안에서 원본을 읽고 씀 | 큰 구조체, 공유 데이터 |
| `VAR_TEMP` | 호출할 때마다 초기화되는 임시 변수 | 중간 계산 |
| `VAR_GLOBAL` / `VAR_EXTERNAL` | 전역 변수 선언 / 다른 POU에서 그 전역 변수 사용 선언 | 구성·리소스 / POU |
| `CONSTANT` 수식어 | 변경 불가 | 설정값 |
| `RETAIN` 수식어 | 전원이 꺼져도 값 유지 | 생산 수량, 누적 시간 |

전역 변수는 어디서 값이 바뀌는지 추적하기 어렵습니다. 장치 상태는 FB 인스턴스의 입출력으로 주고받고, 전역은 I/O 매핑과 HMI 인터페이스 정도로 제한합니다(경험칙).

## 직접 주소와 심볼릭 주소

표준의 직접 표현 변수는 `%` + 위치 + 크기 + 번호 형식입니다.

| 표기 | 의미 |
| --- | --- |
| `%IX0.0` | 입력(I) 비트(X) 0번 바이트의 0번 비트 |
| `%QX0.1` | 출력(Q) 비트 |
| `%IW64` | 입력 워드(16비트). 아날로그 입력 등 |
| `%MW10` | 메모리(M) 워드 |

```text
VAR_GLOBAL
    xStartPb   AT %IX0.0 : BOOL;   (* 시작 버튼 *)
    xConvRun   AT %QX0.0 : BOOL;   (* 컨베이어 접촉기 *)
END_VAR
```

- 로직에는 `%IX0.0` 대신 `xStartPb` 같은 심볼 이름을 씁니다. 배선이 바뀌어도 선언 한 곳만 고치면 됩니다.
- 숫자 주소 형식(`%I0.0`, `X0`, `P00000`, `Local:1:I.Data.0` 등)은 제조사마다 다릅니다. 대응표는 [주소 체계와 도구](../vendors/addressing-and-tools.md)를 참고합니다.
- 최근 도구는 태그(심볼) 기반이 기본이고, 물리 주소는 I/O 구성 화면에서 연결합니다.

## ST 예제: 모터 기능 블록

시작·정지 자기유지, 과부하, 접촉기 피드백 감시를 하나의 FB로 만든 예입니다. 정지 버튼은 단선 시에도 정지하도록 b접점으로 배선했다고 가정합니다(정지 버튼을 누르지 않았을 때 입력이 TRUE).

```text
FUNCTION_BLOCK FB_Motor
VAR_INPUT
    xStartCmd  : BOOL;            (* 시작 요청. 상승 엣지로 넣는 것을 권장 *)
    xStopOk    : BOOL;            (* 정지 버튼 b접점: TRUE = 누르지 않음 *)
    xOverload  : BOOL;            (* 과부하 계전기 트립 *)
    xFeedback  : BOOL;            (* 접촉기 보조 접점 *)
    xReset     : BOOL;            (* 고장 리셋 *)
    tFbTimeout : TIME := T#2S;    (* 피드백 대기 시간 *)
END_VAR
VAR_OUTPUT
    xRun   : BOOL;                (* 접촉기 코일 출력 *)
    xFault : BOOL;
END_VAR
VAR
    tonFb : TON;
END_VAR

(* 출력을 냈는데 피드백이 안 들어오면 고장 *)
tonFb(IN := xRun AND NOT xFeedback, PT := tFbTimeout);

IF xOverload OR tonFb.Q THEN
    xFault := TRUE;                       (* 고장은 리셋 전까지 유지 *)
ELSIF xReset THEN
    xFault := FALSE;
END_IF;

(* 자기유지: 정지와 고장이 시작보다 우선 *)
xRun := (xStartCmd OR xRun) AND xStopOk AND NOT xFault;
END_FUNCTION_BLOCK
```

```text
PROGRAM PLC_PRG
VAR
    fbConveyor : FB_Motor;
    rtStart    : R_TRIG;
END_VAR

rtStart(CLK := xStartPb);
fbConveyor(xStartCmd := rtStart.Q,
           xStopOk   := xStopPb,
           xOverload := xOlTrip,
           xFeedback := xConvFb,
           xReset    := xResetPb);
xConvRun := fbConveyor.xRun;
END_PROGRAM
```

- 시작 신호를 상승 엣지로 넣어 리셋 직후 버튼이 눌린 채로 있어도 바로 재기동하지 않게 합니다.
- 출력 할당(`xConvRun := ...`)은 한 곳에서만 합니다([듀얼 코일 문제](./ladder-basics.md) 참고).
- 이 FB는 학습용입니다. 비상정지는 PLC 로직이 아니라 안전 회로로 처리합니다([비상정지와 인터록](../safety/emergency-stop-and-interlock.md)).

## IEC 61499와의 관계

IEC 61499는 분산 제어를 위한 별도 표준으로, 이벤트 입력으로 실행되는 기능 블록을 여러 장치에 배치하는 모델을 정의합니다. 현재판은 IEC 61499-1:2012(2판)입니다. IEC 61131-3이 "한 PLC 안에서 주기적으로 실행되는 프로그램"을 다룬다면, IEC 61499는 "여러 장치에 나뉜 애플리케이션과 이벤트 흐름"을 다룹니다. 기능 블록 내부 알고리즘은 ST 같은 IEC 61131-3 언어로 작성하는 경우가 많습니다. 최근 동향은 [최신 실무](./modern-practices.md)를 참고합니다.

## 흔한 실수

| 실수 | 결과 | 대응 |
| --- | --- | --- |
| 로직에 직접 주소(`%IX0.3`)를 흩어 씀 | 배선 변경 시 전부 찾아 고쳐야 함 | 심볼 선언 한 곳에서 매핑 |
| 누적값에 `INT` 사용 | 32767 다음 음수로 넘어감 | `DINT`·`UDINT` 사용, 상한 처리 |
| FB 인스턴스를 여러 곳에서 호출 | 타이머·엣지 상태가 꼬임 | 인스턴스 하나는 한 곳에서 한 번 호출 |
| 타이머 FB를 조건문 안에서만 호출 | 조건이 거짓일 때 타이머가 갱신되지 않아 리셋 안 됨 | 타이머는 매 스캔 무조건 호출하고 `IN`으로 제어 |
| 모든 것을 전역 변수로 | 값이 어디서 바뀌는지 추적 불가 | FB 입출력으로 전달 |
