# 마이그레이션과 기술 부채

아키텍처는 한 번에 바꾸지 않습니다. 운영 중인 시스템을 멈추지 않고 **점진적으로** 새 구조로 옮기고, 그 과정에서 쌓이는 부채를 관리하는 방법을 다룹니다.

## 빅뱅 재작성이 실패하는 이유

| 이유 | 설명 |
| --- | --- |
| 숨은 요구 | 기존 시스템의 동작 중 문서화되지 않은 것이 많음 |
| 기간 | 재작성 동안 기존 시스템도 계속 변경되어 목표가 움직임 |
| 가치 지연 | 완성 전까지 사용자에게 아무것도 전달되지 않음 |
| 위험 집중 | 전환 시점에 모든 위험이 한 번에 |

재작성이 정당화되는 경우는 시스템이 작거나, 기술 스택이 유지 불가능하거나, 요구 자체가 바뀐 때로 제한됩니다.

## 스트랭글러 패턴

새 시스템이 기존 시스템을 조금씩 감싸며 대체합니다.

```mermaid
flowchart LR
    C[클라이언트] --> F[파사드·라우터]
    F -->|이전된 기능| N[새 모듈·서비스]
    F -->|나머지| L[기존 시스템]
    N -.->|필요 시| L
```

| 단계 | 내용 |
| --- | --- |
| 1 | 진입점 앞에 파사드(프록시, API 게이트웨이, 라우팅 계층) 설치 |
| 2 | 기능 하나를 새 구조로 구현. 경계가 분명하고 의존이 적은 것부터 |
| 3 | 파사드에서 해당 요청만 새 구현으로 라우팅. 기능 플래그로 비율 조절 |
| 4 | 비교·검증 후 기존 코드 제거 |
| 5 | 반복. 기존 시스템이 비면 파사드 제거 |

| 선택 순서 기준 | 이유 |
| --- | --- |
| 변경이 잦은 기능 | 새 구조의 이점이 빨리 나타남 |
| 의존이 적은 기능 | 데이터 분리가 쉬움 |
| 위험이 낮은 기능 | 초기 실패의 영향 제한 |

## 데이터 이전

코드보다 데이터 이전이 어렵습니다. 읽기·쓰기 경로를 단계적으로 바꿉니다.

| 단계 | 쓰기 | 읽기 | 검증 |
| --- | --- | --- | --- |
| 1. 이중 쓰기 | 기존 + 새 저장소 | 기존 | 두 저장소 비교 |
| 2. 백필 | 기존 데이터를 새 저장소로 복사 | 기존 | 건수·체크섬 |
| 3. 그림자 읽기 | 양쪽 | 기존 응답, 새 결과는 비교만 | 불일치 로그 |
| 4. 전환 | 양쪽 | 새 저장소 | 오류율·지연 |
| 5. 정리 | 새 저장소만 | 새 저장소 | 기존 저장소 읽기 전용 → 삭제 |

| 주의 | 대응 |
| --- | --- |
| 이중 쓰기 중 한쪽 실패 | 아웃박스·재시도, 불일치 복구 작업 |
| 스키마 차이 | 변환 계층, 역방향 변환도 준비(롤백) |
| 롤백 | 각 단계에서 이전 단계로 돌아갈 수 있어야 진행 |

## 모듈 추출 절차

모놀리스에서 모듈 또는 서비스를 떼어낼 때의 순서입니다.

| 단계 | 내용 | 확인 |
| --- | --- | --- |
| 1 | 대상 코드의 현재 의존(들어오고 나가는 것) 측정 | 의존성 그래프 |
| 2 | 안에서 밖으로 나가는 호출을 인터페이스 뒤로 | 도메인이 인프라를 모름 |
| 3 | 밖에서 안으로 들어오는 접근을 공개 API로 제한 | 내부 직접 접근 0 |
| 4 | 데이터 소유권 분리(스키마·접근 경로) | 타 모듈의 테이블 접근 0 |
| 5 | 의존 규칙을 피트니스 함수로 고정 | CI 통과 |
| 6 | (서비스 분리 시) 인프로세스 호출을 네트워크 호출로, 이벤트로 | 지연·오류 측정 |

5단계까지는 배포 단위를 바꾸지 않습니다. 대부분은 여기서 멈춰도 충분합니다.

## 기술 부채

| 종류 | 예 | 성격 |
| --- | --- | --- |
| 의도적·신중한 | "출시를 위해 캐시 없이 가고 2주 후 추가" | 기록된 결정, 상환 계획 있음 |
| 의도적·무모한 | "설계할 시간 없음" | 비용 인식 없이 누적 |
| 비의도적·신중한 | "지금 알게 된 것으로는 다르게 했을 것" | 학습의 결과, 자연스러움 |
| 비의도적·무모한 | 원칙을 몰라서 | 교육·리뷰로 예방 |

| 관리 | 방법 |
| --- | --- |
| 가시화 | 부채 항목을 이슈로 등록. 위치, 영향(변경 비용·장애·성능), 상환 비용 |
| 우선순위 | 영향 × 변경 빈도. 안 건드리는 코드의 부채는 후순위 |
| 예산 | 스프린트·분기마다 일정 비율(예: 20%)을 상환에 |
| 보이스카우트 규칙 | 건드린 코드는 조금 더 낫게 |
| 측정 | 리드 타임, 변경 실패율, 핫스팟(자주 바뀌고 복잡한 파일) |
| 기록 | 큰 부채는 ADR에 "의도적으로 미룸"으로 명시 |

## 전환 중 유지할 것

| 항목 | 내용 |
| --- | --- |
| 기능 동등성 테스트 | 기존·새 구현에 같은 입력, 같은 출력 확인 |
| 관측 | 새 경로의 오류·지연을 기존과 나란히 |
| 기능 플래그 | 즉시 되돌릴 수 있는 스위치 |
| 작은 배포 | 단계마다 배포. 장기 브랜치 금지 |
| 종료 기준 | 기존 코드 삭제까지가 완료. "둘 다 유지"는 부채 |
