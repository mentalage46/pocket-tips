# 문맥과 지식 축적

에이전트의 성능은 모델만큼이나 **읽을 수 있는 지식**에 좌우됩니다. 담당자 머릿속에만 있는 규칙, 채팅에 흩어진 결정, 오래된 문서는 에이전트가 쓸 수 없습니다. 이 문서는 팀의 지식을 에이전트가 쓸 수 있는 형태로 쌓는 방법을 다룹니다.

## 지식의 층

| 층 | 내용 | 두는 곳 | 읽히는 시점 |
| --- | --- | --- | --- |
| 프로젝트 지침 | 빌드·테스트 명령, 코드 규칙, 금지 사항, 디렉터리 안내 | 저장소 루트의 지침 파일 | 매 세션 시작 |
| 영역 지침 | 특정 디렉터리·패키지의 규칙 | 해당 디렉터리의 지침 파일 | 그 영역 작업 시 |
| 절차(스킬) | 반복 작업의 순서와 체크리스트 | 스킬·명령 파일 | 해당 작업 요청 시 |
| 설계 기록 | 왜 그렇게 결정했는지(ADR), 스펙 | `docs/` | 설계·변경 시 검색 |
| 운영 지식 | 런북, 장애 기록, 환경 정보 | `docs/` 또는 운영 저장소 | 운영 작업 시 |
| 개인·팀 메모리 | 선호, 과거 피드백, 진행 중인 작업 | 에이전트 메모리 저장소 | 관련 작업 시 회상 |

## 프로젝트 지침 파일

Claude Code의 `CLAUDE.md`, 여러 도구가 읽는 `AGENTS.md`, Cursor의 규칙 파일처럼 **저장소에 두는 에이전트용 README**입니다. 이름은 도구마다 다르지만 내용은 비슷합니다.

| 넣을 것 | 예 |
| --- | --- |
| 명령 | `npm test`, `npm run build`, `npm run check-links` |
| 구조 | 주요 디렉터리와 역할, 진입점 |
| 규칙 | 스타일, 커밋 규칙, 테스트 필수 여부, 금지 API |
| 작업 절차 | "문서를 추가하면 README에 링크하고 manifest를 다시 만든다" |
| 함정 | 자주 틀리는 부분, 느린 명령, 외부 의존성 |

| 넣지 말 것 | 이유 |
| --- | --- |
| 코드로 알 수 있는 것 | 금방 낡음. 코드를 읽게 하는 편이 정확 |
| 긴 설명 | 매 세션 읽히므로 문맥 비용. 자세한 내용은 문서로 링크 |
| 일회성 작업 지시 | 지침 파일은 오래 남는 규칙만 |

이 저장소의 `.agent/rules/guide-line.md`가 같은 역할을 합니다. 문서 추가 시 README 링크와 manifest 갱신 규칙이 적혀 있습니다.

## 스킬과 절차 문서

반복되는 작업은 절차를 파일로 만들어 에이전트가 요청 시 읽게 합니다.

```text
이름: release-notes
언제: 릴리스 태그를 만들 때
입력: 이전 태그 이후의 PR 목록
절차:
  1. PR을 유형(기능, 수정, 문서, 내부)으로 분류
  2. 사용자에게 보이는 변경만 요약, 내부 변경은 한 줄로 묶음
  3. 깨지는 변경(breaking)은 맨 위에 마이그레이션 안내와 함께
출력: CHANGELOG.md 상단에 추가할 Markdown
검증: 링크된 PR 번호가 모두 존재
```

절차 문서는 "어떻게 하라"보다 **"무엇을 확인하라"**를 담을 때 오래갑니다. 도구 사용법은 바뀌지만 확인 항목은 덜 바뀝니다.

## 설계 기록(ADR)

| 항목 | 내용 |
| --- | --- |
| 제목·날짜·상태 | 제안, 채택, 폐기, 대체됨 |
| 맥락 | 어떤 문제와 제약이 있었는가 |
| 결정 | 무엇을 선택했는가 |
| 대안 | 고려했으나 택하지 않은 것과 이유 |
| 결과 | 얻는 것과 감수하는 것 |

에이전트가 설계 작업 전에 ADR 디렉터리를 검색하도록 지침에 적어 두면, 이미 폐기된 방안을 다시 제안하는 일이 줄어듭니다.

## 메모리

| 종류 | 내용 | 주의 |
| --- | --- | --- |
| 사용자 | 역할, 선호(언어, 형식), 자주 쓰는 도구 | 추측이 아니라 확인된 것만 |
| 피드백 | "이렇게 하지 말라"는 교정과 그 이유 | 이유를 함께 남겨야 다른 상황에 적용 가능 |
| 프로젝트 | 진행 중인 작업, 마감, 코드로 알 수 없는 제약 | 상대 날짜는 절대 날짜로 |
| 참조 | 대시보드, 티켓, 외부 문서 링크 | 링크가 살아 있는지 가끔 확인 |

저장소에서 알 수 있는 것(구조, 과거 수정, 커밋 이력)은 메모리에 넣지 않습니다. 메모리는 **저장소 밖에 있던 지식**을 담습니다.

## 문맥 예산

| 전략 | 방법 |
| --- | --- |
| 필요한 것만 | 전체 파일 대신 관련 심볼·구간. 검색 → 읽기 순서 |
| 요약과 링크 | 지침 파일은 짧게, 자세한 내용은 문서 경로로 연결 |
| 분할 | 긴 작업은 단계로 나누고 단계마다 상태를 파일에 기록 |
| 하위 에이전트 | 조사처럼 출력이 큰 작업은 따로 실행해 결론만 받음 |
| 재주입 | 긴 세션 후에는 규칙 파일을 다시 읽게 함 |

## 문서 구조 권장

```text
docs/
  README.md            목차와 학습 순서
  specs/               기능 스펙 (날짜-주제.md)
  adr/                 설계 결정 기록
  runbooks/            운영 절차
  <영역>/README.md     영역별 목차
```

사람이 읽기 좋은 구조가 에이전트에게도 좋습니다. 이 저장소처럼 폴더마다 README에 목차를 두고 상대 링크로 연결하면, 에이전트가 디렉터리를 훑는 대신 목차에서 출발할 수 있습니다.

## 에이전트 온보딩 체크리스트

- [ ] 빌드·테스트·린트 명령이 지침 파일에 있다
- [ ] 디렉터리 구조와 진입점이 설명되어 있다
- [ ] 금지 사항(건드리지 말 파일, 쓰지 말 API, 커밋·푸시 규칙)이 명시되어 있다
- [ ] 반복 작업의 절차가 스킬·명령 파일로 있다
- [ ] 설계 결정이 ADR로 남아 있고 검색 가능하다
- [ ] 테스트가 실제 요구를 검증한다(에이전트의 완료 기준이 됨)
- [ ] 문서의 링크가 깨지지 않았다(링크 검사 자동화)
- [ ] 새 규칙이 생기면 지침 파일을 갱신하는 담당과 시점이 정해져 있다
