# 배포 전략과 롤백

배포 전략은 **새 버전을 어떤 순서로 사용자에게 노출하고, 문제가 생기면 어떻게 되돌릴지** 정하는 방법입니다. 파이프라인이 아무리 빨라도 되돌리는 방법이 없으면 배포 빈도를 올릴 수 없습니다.

## 전략 비교

| 전략 | 방식 | 필요한 자원 | 롤백 | 적합한 상황 |
| --- | --- | --- | --- | --- |
| 재생성(Recreate) | 기존 버전을 내리고 새 버전을 올림 | 1벌 | 이전 이미지로 다시 재생성 | 다운타임 허용, 1인 사이드 프로젝트 |
| 롤링(Rolling) | 인스턴스를 하나씩 교체 | 1벌 + 여유 1대 | 역방향 롤링 | 여러 인스턴스, 신·구 버전 공존 가능 |
| 블루-그린(Blue-Green) | 새 환경(그린)을 띄운 뒤 트래픽을 한 번에 전환 | 2벌 | 트래픽을 블루로 되돌림 | 빠른 전환·롤백이 중요할 때 |
| 카나리(Canary) | 일부 트래픽(예: 5%)에만 새 버전 노출 후 확대 | 2벌 + 트래픽 분할 | 비율을 0으로 | 사용자 수가 많고 지표로 판단 가능할 때 |
| 기능 플래그(Feature Flag) | 코드는 배포하고 기능 노출은 설정으로 제어 | 플래그 저장소 | 플래그 끄기 | 배포와 출시를 분리하고 싶을 때 |

```text
Recreate     [v1 v1] → [  ] → [v2 v2]           (짧은 중단)
Rolling      [v1 v1] → [v2 v1] → [v2 v2]
Blue-Green   LB → blue(v1)   ⇒   LB → green(v2)  (blue는 대기)
Canary       LB → v1 95% / v2 5% → 50% → 100%
```

## 1인·소규모에서의 선택

트래픽 분할이나 서비스 메시가 필요한 카나리는 운영 비용이 큽니다. 작은 규모에서는 아래 순서로 단계를 올리는 편이 현실적입니다(경험칙).

1. **재생성 + 헬스체크**: `docker compose pull && docker compose up -d`. 중단 시간이 수 초 생깁니다.
2. **리버스 프록시 앞단 무중단 교체**: 새 컨테이너가 헬스체크를 통과하면 프록시가 트래픽을 넘깁니다. Kamal의 kamal-proxy, Coolify·Dokploy의 Traefik 연동이 이 방식을 자동화합니다. 자세한 도구는 [1인·소규모 도구 선택](./solo-dev-tools.md)을 참고합니다.
3. **관리형 플랫폼의 불변 배포**: Vercel·Netlify·Cloudflare 등은 배포마다 새 URL을 만들고 별칭(도메인)만 옮깁니다. 이전 배포로 별칭을 되돌리는 것이 곧 롤백입니다.
4. **기능 플래그**: 위험한 기능만 플래그 뒤에 숨깁니다. 처음에는 환경변수나 DB 설정값 하나로 충분합니다.

## 롤백 설계

| 항목 | 지켜야 할 것 |
| --- | --- |
| 아티팩트 보관 | 이전 버전 이미지·번들을 지우지 않습니다. `latest`만 쓰면 되돌릴 대상이 사라집니다 |
| 불변 태그 | 커밋 SHA나 시맨틱 버전 태그로 배포합니다. 같은 태그를 덮어쓰지 않습니다 |
| 롤백 명령 | 한 줄로 실행할 수 있게 만듭니다. 예: `IMAGE_TAG=<이전 SHA> docker compose up -d` |
| DB 마이그레이션 | 롤백이 가장 어려운 부분입니다. 아래 확장-축소 패턴을 씁니다 |
| 판단 기준 | 에러율, 응답 시간, 헬스체크 실패 등 "되돌릴 조건"을 미리 정합니다 |

### DB 마이그레이션: 확장-축소(Expand-Contract)

코드와 스키마를 한 번에 바꾸면 롤백한 코드가 새 스키마에서 깨집니다. 변경을 여러 번의 배포로 나눕니다.

| 단계 | 스키마 | 코드 | 롤백 가능 여부 |
| --- | --- | --- | --- |
| 1. 확장 | 새 컬럼 추가(nullable) | 기존 컬럼만 사용 | 가능 |
| 2. 이중 쓰기 | 그대로 | 기존·새 컬럼 모두 기록, 데이터 백필 | 가능 |
| 3. 전환 | 그대로 | 새 컬럼에서 읽기 | 가능(기존 컬럼도 최신) |
| 4. 축소 | 기존 컬럼 삭제 | 새 컬럼만 사용 | 이 단계 이후 되돌리기 어려움 |

마이그레이션은 앱 시작 시 자동 실행하기보다 파이프라인의 별도 단계로 두면 실패 지점을 구분하기 쉽습니다.

## 배포 후 확인

```bash
# 배포 직후 스모크 테스트 예시
for i in $(seq 1 10); do
  curl -fsS https://example.com/health && exit 0
  sleep 3
done
echo "health check failed" && exit 1
```

- 헬스체크 엔드포인트는 앱 프로세스뿐 아니라 DB 연결 등 핵심 의존성도 확인합니다. 단, 외부 API 장애로 전체가 내려가지 않도록 범위를 정합니다.
- 실패하면 파이프라인이 자동으로 이전 태그를 다시 배포하거나, 최소한 알림을 보냅니다.

## 점검표

| 질문 |
| --- |
| 이전 버전 아티팩트가 레지스트리에 남아 있는가 |
| 롤백을 한 줄 명령 또는 버튼 하나로 할 수 있는가 |
| 마이그레이션이 직전 버전 코드와 호환되는가 |
| 배포 후 헬스체크 실패를 자동으로 감지하는가 |
| 되돌릴 조건(지표·임계값)을 미리 정했는가 |
