# Code Review Guide

## 코드 리뷰의 목적

> 코드 품질 향상 + 지식 공유 + 버그 사전 발견

**좋은 코드 리뷰의 효과**

- 버그 조기 발견
- 코드 품질 향상
- 팀 전체 지식 수준 상승
- 코드베이스 일관성 유지

---

## 개념: 리뷰의 기준은 "완벽함"이 아니라 "코드가 더 나아지는가"다

### 승인의 기준

Google의 코드 리뷰 가이드(공개 문서)는 이렇게 정합니다. 리뷰어는 변경이 **전체적인 코드 건강도(code health)를 분명히 개선하는 상태**가 되면 승인을 우선해야 하고, 가이드는 **"완벽한 코드는 없고 더 나은 코드만 있다"**고 말합니다.

- 리뷰어가 완벽을 요구하면 작성자는 사소한 다듬기에 시간을 쓰고 팀 속도가 떨어집니다. 반대로 기준이 없으면 코드베이스가 조금씩 나빠집니다. 기준은 **"이 변경 후 코드베이스가 이전보다 낫거나 최소한 나빠지지 않았는가"**입니다.
- **스타일은 스타일 가이드가 최종 권위**입니다. 가이드에 없는 것은 개인 취향이므로 개인 선호만으로 승인을 막지 않습니다. 가이드에 이전 선례가 없으면 대개 작성자의 선택을 존중합니다.
- 그래서 필수가 아닌 제안에는 **`Nit:`** 같은 접두사를 붙여 "무시해도 된다"는 신호를 줍니다. 아래 코멘트 접두사 제안이 이 취지입니다.

### 무엇을 어떤 순서로 보는가

Google 가이드의 우선순위를 요약하면 다음과 같습니다. 위쪽일수록 중요하고 고치기 비쌉니다.

| 순위 | 항목 | 질문 |
| --- | --- | --- |
| 1 | **설계** | 변경의 전체 구조가 적절한가, 시스템 안에서 이 위치가 맞는가 (리뷰에서 가장 중요) |
| 2 | **기능** | 작성자가 의도한 대로 동작하는가, 사용자에게 좋은 동작인가 |
| 3 | **복잡도** | 코드를 읽는 사람이 빠르게 이해할 수 있는가, 지금 필요하지 않은 일반화(과잉 설계)를 하지 않았는가 |
| 4 | **테스트** | 변경에 맞는 단위·통합·E2E 테스트가 있는가 |
| 5 | 이름, 주석 | 이름이 좋은가, 주석이 "무엇"이 아니라 **"왜"**를 설명하는가 |
| 6 | 스타일, 일관성, 문서 | 스타일 가이드를 따르는가, 문서가 필요하면 있는가 |

- **맡은 모든 줄을 읽습니다.** 변경된 줄만이 아니라 **주변 파일과 시스템**을 보고, 코드 건강도를 떨어뜨리는 변경은 승인하지 않습니다.
- **잘한 점을 말해 줍니다.** 좋은 부분을 알리면 그 방식이 반복됩니다.
- **설계 문제는 코드를 다 쓰기 전에** 발견해야 비용이 낮습니다. 큰 변경은 코드를 쓰기 전에 설계를 합의합니다([ADR](../../Architecture/process/adr.md)).
- 포맷·린트·타입 같은 **기계가 판단할 수 있는 것**은 사람이 리뷰하지 말고 자동화에 맡깁니다. 사람의 시간은 설계와 의도 같은 기계가 못 보는 것에 씁니다(일반 원칙).

### 속도: 응답 시간이 팀 속도를 정한다

Google 가이드는 코드 리뷰 요청에 **응답하는 데 걸리는 최대 시간을 영업일 하루**로 정하고, 리뷰어가 가능하면 더 빨리 답하라고 합니다.

- 기준은 전체 리뷰가 끝나는 시간이 아니라 **각 단계의 응답 시간**입니다. 빠른 응답이 여러 번 오가는 편이 한 번의 긴 리뷰보다 낫습니다.
- 한 사람의 속도가 아니라 **팀 전체가 제품을 만드는 속도**를 최적화합니다. 리뷰가 늦으면 작성자가 막히고 다른 일의 속도도 떨어집니다.
- 반대로 리뷰어도 **집중해서 코드를 쓰는 중이라면 중단하지 않습니다.** 작업이 끝났을 때, 점심 뒤, 회의 뒤 같은 **자연스러운 휴식 시점**에 리뷰합니다.

### 작은 변경이 리뷰를 살린다

Google 가이드가 드는 작은 변경의 이점입니다.

| 이점 | 이유 |
| --- | --- |
| 더 빨리 리뷰됨 | 리뷰어가 5분을 여러 번 내기 쉬움 |
| 더 철저히 리뷰됨 | 큰 변경은 주고받는 코멘트가 많아 중요한 지적이 묻힘 |
| 버그가 적음 | 작은 변경의 영향은 추론하기 쉬움 |
| 낭비 감소 | 방향이 거부돼도 버려지는 작업이 적음 |
| 병합이 쉬움 | 오래 걸린 변경일수록 충돌이 많아짐 |
| 롤백이 간단함 | 건드린 파일이 적음 |

- **"작다"의 기준은 줄 수가 아니라 "하나의 자기 완결적인 변경"입니다.** 가이드는 하나를 다루고, 관련 테스트를 포함하며, 제출 후에도 시스템이 동작하는 변경이라고 정의합니다. 정확한 한계는 없지만 **약 100줄은 대개 적당하고 1,000줄은 대개 너무 크며**, 파일 수도 영향을 줍니다(한 파일 200줄은 괜찮아도 50개 파일에 퍼진 200줄은 크다). 확신이 없으면 더 작게 만듭니다.
- 이 문서 아래의 "파일 10개, 400줄, 30분"은 널리 쓰이는 **경험칙**이며 공식 기준이 아닙니다. 팀의 상황에 맞게 조정합니다.
- **리팩터링은 기능·버그 수정과 분리**합니다. 클래스 이동·이름 변경은 별도 변경으로 내고, 지역 변수 이름 변경 같은 작은 정리는 같이 넣어도 됩니다. 섞여 있으면 리뷰어가 의미 있는 변경을 가려내기 어렵습니다.

### 의견이 갈릴 때

1. 작성자와 리뷰어가 **먼저 합의**를 시도합니다. 글로 안 풀리면 **대면·화상으로 이야기**합니다.
2. 합의 결과를 **변경에 기록**합니다(나중에 읽는 사람이 이유를 알 수 있게).
3. 그래도 해결이 안 되면 더 넓은 팀 논의, 기술 리드, 코드 소유자, 매니저에게 **에스컬레이션**합니다.
4. 가이드의 원칙: **"작성자와 리뷰어가 합의하지 못한다는 이유로 변경을 방치하지 않는다."**

### 한계: 리뷰만으로는 부족하다

리뷰어도 모든 버그를 잡지 못합니다(일반 개념). 리뷰는 **설계·가독성·지식 공유**에 강하고, 회귀 방지는 **테스트와 CI**의 몫입니다. 리뷰어가 "테스트가 이 동작을 검증하는가"를 묻는 것이 리뷰와 테스트를 잇는 고리입니다([테스트 전략](../../Backend/testing/testing-strategy.md)).

## 리뷰어 가이드

### 리뷰 관점

| 관점           | 확인 사항            |
| -------------- | -------------------- |
| **정확성**     | 의도대로 동작하는가? |
| **설계**       | 구조가 적절한가?     |
| **가독성**     | 이해하기 쉬운가?     |
| **유지보수성** | 변경하기 쉬운가?     |
| **성능**       | 성능 문제 없는가?    |
| **보안**       | 취약점 없는가?       |
| **테스트**     | 테스트 충분한가?     |

### 좋은 코멘트 작성법

```
# ✅ 좋은 코멘트
"이 로직은 O(n²)인데, Map을 사용하면 O(n)으로 개선할 수 있을 것 같아요."
"null 체크가 없어서 이 경우에 에러가 날 수 있어요. Optional 처리는 어떨까요?"

# ❌ 나쁜 코멘트
"이거 이상해요"
"왜 이렇게 했어요?"
"잘못됐습니다"
```

### 코멘트 접두사 (선택)

```
[필수] 반드시 수정이 필요합니다.
[제안] 개선 제안입니다. 반영 여부는 자유입니다.
[질문] 이해가 안 되어 질문합니다.
[칭찬] 좋은 부분입니다!
[논의] 논의가 필요합니다.
```

### 리뷰 우선순위

```
1. 버그 / 보안 이슈     → 반드시 수정
2. 설계 / 아키텍처      → 중요, 논의 필요
3. 성능 문제            → 중요도에 따라
4. 가독성 / 네이밍      → 가능하면 개선
5. 스타일 / Nitpick     → 선택적
```

## 작성자 가이드

### PR 작성 시

```markdown
## 개요

- 이 PR의 목적과 배경

## 변경 사항

- 주요 변경 내용 (bullet point)

## 테스트

- 테스트 방법 또는 결과

## 스크린샷 (UI 변경 시)

## 체크리스트

- [ ] 테스트 추가/수정
- [ ] 문서 업데이트
- [ ] Breaking change 없음
```

### PR 크기

```
# 권장 크기 (경험칙, 공식 기준 아님)
- 파일: 10개 이하
- 변경 줄: 400줄 이하 (Google 가이드는 약 100줄을 적당, 1,000줄을 과대로 봄)
- 리뷰 시간: 30분 이내

# 큰 PR 쪼개기
기능 A + 기능 B + 리팩토링
→ PR 1: 리팩토링
→ PR 2: 기능 A
→ PR 3: 기능 B
```

### Self-Review

```
PR 생성 전 본인이 먼저 확인:
- [ ] 불필요한 console.log / 디버그 코드 제거
- [ ] 하드코딩된 값 없는지
- [ ] 주석 정리
- [ ] 테스트 통과
- [ ] 린트 에러 없음
```

## 리뷰 체크리스트

### 기능

- [ ] 요구사항대로 동작하는가?
- [ ] 엣지 케이스 처리했는가?
- [ ] 에러 처리가 적절한가?

### 설계

- [ ] 단일 책임 원칙을 따르는가?
- [ ] 중복 코드는 없는가?
- [ ] 의존성이 적절한가?
- [ ] 확장하기 쉬운 구조인가?

### 가독성

- [ ] 변수/함수명이 명확한가?
- [ ] 복잡한 로직에 주석이 있는가?
- [ ] 함수 길이가 적절한가?
- [ ] 중첩이 깊지 않은가?

### 성능

- [ ] 불필요한 연산은 없는가?
- [ ] N+1 쿼리 문제는 없는가?
- [ ] 메모리 누수 가능성은 없는가?
- [ ] 적절한 자료구조를 사용했는가?

### 보안

- [ ] SQL Injection 방지했는가?
- [ ] XSS 방지했는가?
- [ ] 민감정보 노출은 없는가?
- [ ] 인증/인가 체크했는가?

### 테스트

- [ ] 테스트가 추가되었는가?
- [ ] 핵심 로직이 테스트되었는가?
- [ ] 테스트가 의미있는가?

## 피드백 받을 때

### Do's

```
✅ 피드백을 개인 공격으로 받아들이지 않기
✅ 왜 그렇게 했는지 설명하기
✅ 동의하면 빠르게 반영
✅ 동의하지 않으면 근거와 함께 논의
✅ 배움의 기회로 생각하기
```

### Don'ts

```
❌ 방어적으로 반응하기
❌ 코멘트 무시하기
❌ "동작하는데 왜요?" 라고 하기
❌ 감정적으로 대응하기
```

## 리뷰 문화

### 좋은 문화

```
- "코드"를 리뷰하지 "사람"을 리뷰하지 않는다
- 질문을 환영한다
- 칭찬을 아끼지 않는다
- 작은 PR을 권장한다
- 빠른 리뷰를 지향한다 (응답은 영업일 하루 이내가 상한, Google 가이드)
```

### 리뷰 시간 관리

```
# 리뷰어
- 알림 확인: 오전/오후 정해진 시간
- 리뷰 소요: PR당 15~30분 목표
- 응답: 24시간 내

# 작성자
- 리뷰 요청 전 self-review
- 피드백 반영: 빠르게
- 논의 필요 시: 대면/화상 미팅
```

## 🎯 상황별 리뷰 체크리스트

### 새로운 기능

- [ ] 요구사항 충족
- [ ] API 설계 적절
- [ ] 테스트 커버리지
- [ ] 문서 업데이트

### 버그 수정

- [ ] 근본 원인 해결
- [ ] 사이드 이펙트 없음
- [ ] 재현 테스트 추가
- [ ] 같은 패턴 다른 곳에 없는지

### 리팩토링

- [ ] 기능 변경 없음
- [ ] 테스트 유지/개선
- [ ] 점진적 변경
- [ ] 성능 저하 없음

### 성능 개선

- [ ] 벤치마크 결과 첨부
- [ ] 가독성 희생 최소화
- [ ] 사이드 이펙트 없음
